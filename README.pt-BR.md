## Status atual

**Fase 0 (fundação) concluída.** Monorepo, auth multi-tenant (registro/login/refresh com trial), RBAC via CASL, RLS no Postgres, CI — tudo validado contra banco real.

**Fase 1 (MVP comercial) concluída** — Cadastros, PDV, Estoque básico, Financeiro básico, fiscal e pagamento integrado (sandbox), job de trial e gestão de usuários:

- **Cadastros:** categorias, produtos, clientes e fornecedores — CRUD completo, multi-tenant de verdade via RLS, RBAC via CASL (`operador_caixa` só lê; `admin`/`owner` gerenciam; `financeiro` só lê). Preço sempre em centavos (inteiro), nunca float. Produto não tem exclusão definitiva — só `active: false` — porque venda referencia produto e apagar quebraria histórico.
- **PDV:** abertura/fechamento de caixa, sangria/suprimento, venda de balcão com múltiplos itens e pagamento dividido entre formas (dinheiro/cartão/Pix). Venda exige caixa aberto do próprio operador; total da venda precisa bater exatamente com a soma dos pagamentos informados; item de venda guarda snapshot do nome/preço do produto (preço pode mudar depois, histórico não). Quantidade é sempre inteira — venda fracionada/por peso fica para quando o público-alvo (mercearia, loja, pet shop, farmácia, conveniência) exigir.
- **Estoque básico:** entrada, saída e ajuste de saldo por produto, com ledger auditável (`stock_movements`) e saldo denormalizado no próprio produto. Venda no PDV desconta o estoque automaticamente dentro da mesma transação (ou os dois acontecem, ou nenhum) e bloqueia a venda se não houver saldo suficiente. Produtos podem opcionalmente sair do controle de estoque (`trackStock: false`) para itens sob encomenda ou serviços. Movimentação manual é restrita a `admin`/`owner` (`financeiro` só lê; `operador_caixa` não movimenta diretamente, só via venda).
- **Financeiro básico:** contas a pagar e a receber (`finance_entries`) com vencimento, status (pendente/paga/cancelada) e vínculo opcional a cliente ou fornecedor. Pagamento é sempre integral — sem pagamento parcial na Fase 1. Resumo de fluxo de caixa (`GET /finance-entries/summary`) soma pendente, vencido e realizado (pago) por tipo. Gestão é exclusiva de `admin`/`owner`/`financeiro`; `operador_caixa` não acessa. Contas ainda não se conectam a vendas a prazo — é um ledger manual independente do PDV por enquanto.
- **Fiscal e pagamento integrado (sandbox):** seguindo a recomendação do [docs/03](docs/03-build-vs-buy-pagamentos-fiscal.md), o resto do sistema fala com interfaces internas (`PaymentProvider`, `FiscalProvider`), não com o gateway/fiscal diretamente — trocar de fornecedor é escrever um adapter novo. Hoje ambas usam um adapter mock (nenhuma conta/credencial de parceiro existe ainda): pagamento em cartão/Pix é "cobrado" e recebe um `providerTransactionId`; toda venda emite automaticamente uma NFC-e simulada (`fiscal_documents`, chave de 44 dígitos) sem travar a venda se o "provedor" falhar (contingência) — nesse caso fica com status `rejected` e pode ser reemitida via `POST /sales/:id/fiscal-document/retry` (só `admin`/`owner`). Pagamento recusado pelo gateway cancela a venda inteira (mesma transação do estoque/itens). Ir para produção real exige só trocar o adapter por Pagar.me/Mercado Pago e Focus NFe/PlugNotas/eNotas, quando houver conta e credenciais.
- **Job de expiração de trial:** roda de hora em hora (`@nestjs/schedule`) e sincroniza `tenants.status` para `blocked` quando o trial vence. O bloqueio de acesso em si já era em tempo real (`TenantStatusGuard` compara `trialEndsAt` a cada request) — o job só mantém o status persistido fiel à realidade.
- **Gestão de usuários:** convite por e-mail (Resend) com token de uso único (hash bcrypt, expira em 7 dias, `/painel/usuarios`), aceite com login automático (`/aceitar-convite`), promoção/rebaixamento de papel com a regra de sempre existir ao menos um `owner` por tenant. Só `admin`/`owner` gerenciam usuários; só um `owner` pode convidar/promover outro `owner`. Segue o mesmo padrão de adapter interno (`EmailProvider`) do pagamento/fiscal — trocar de provedor de e-mail é só a classe.
- Frontend: `/painel/produtos` (cadastro + saldo de estoque + movimentação), `/painel/pdv` (abrir caixa, montar carrinho, pagamento dividido, sangria/suprimento, fechar caixa, confirmação de NFC-e sandbox), `/painel/financeiro` (contas a pagar/receber + resumo de fluxo de caixa) e `/painel/usuarios` (convidar, listar, promover/rebaixar)
- 49 testes e2e contra Postgres real cobrindo CRUD, isolamento entre tenants (RLS — inclusive um teste que verifica o privilégio da própria role de banco, não só o filtro da aplicação), RBAC, regras de negócio do PDV, desconto atômico de estoque, ciclo de vida financeiro, emissão fiscal (contingência/reemissão), recusa de pagamento pelo gateway, expiração de trial, convite/gestão de usuários (incluindo atomicidade quando o envio de e-mail falha) e logout/revogação de refresh token

Com isso os seis itens de Fase 1 do roadmap estão implementados, as duas pendências que ficavam para depois (trial automático, gestão de usuários) foram fechadas, e uma falha crítica de isolamento entre tenants foi encontrada e corrigida (a role de banco usada em runtime era superuser e ignorava RLS por completo — ver migration `0011_app_role_least_privilege`). O que falta para produção real de fiscal/pagamento é uma decisão de negócio (qual parceiro, criar a conta) — não código; ver [docs/03](docs/03-build-vs-buy-pagamentos-fiscal.md).

**Hardening de segurança pós-revisão:** o código foi auditado (revisão automatizada + IA externa) antes de ir para o GitHub público. Achados reais corrigidos: `updateRole` tinha dois bypasses de autorização (admin rebaixando owner; usuário rebaixado se auto-promovendo com o access token antigo antes de expirar); o e-mail de convite interpolava nome do convidante/empresa sem escape de HTML (injeção de link de phishing num e-mail assinado); não havia como revogar um refresh token (só rotação no uso — `POST /auth/logout` agora existe e é chamado pelo botão "Sair"); faltavam headers de segurança (`helmet`); `register`/`invite`/`accept-invite` só tinham o rate-limit genérico da API (100/min), agora têm limite próprio; `CORS_ORIGIN` não era validado como URL. Itens reais mas adiados por serem features maiores, não fixes pontuais: reset de senha, 2FA, bloqueio de conta após tentativas falhas, log de auditoria de ações privilegiadas — ver issues/roadmap.

**Fase 2 (consolidação) — em andamento.** Primeiro módulo: **Compras**.

- **Compras:** pedido de compra a fornecedor (`purchase_orders`/`purchase_order_items`, snapshot de nome/custo do produto no momento do pedido, mesmo padrão de `sale_items`) com três estados — `draft` (rascunho, editável só por recriação), `received` (recebido) e `canceled` (só a partir de rascunho). Sem estado "enviado ao fornecedor": não existe integração real de notificação ainda, um status sem comportamento por trás seria estado morto (mesmo raciocínio do sandbox fiscal/pagamento). Receber um pedido é atômico com o Estoque: gera entrada (`stock_movements`, reaproveitando `StockService.applyMovement`) para cada item com `trackStock` ativo, e atualiza `products.costPriceCents` com o último custo de compra. Cancelamento só é permitido em rascunho (recebido não se desfaz sozinho — evita ter que reverter estoque). RBAC via CASL: `admin`/`owner` gerenciam, `financeiro` só lê (cuida de custo), `operador_caixa` sem acesso. Frontend em `/painel/compras`. Deliberadamente desacoplado do Financeiro por ora — receber um pedido não gera conta a pagar automaticamente (o usuário lança manualmente se quiser); acoplar os dois é decisão para quando "Financeiro avançado" (outro item da Fase 2) entrar.
- 6 testes e2e novos cobrindo o fluxo completo (criar → receber → estoque/custo atualizados), transições de estado inválidas, isolamento entre tenants e RBAC.
- 5 testes e2e novos para Relatórios cobrindo agregação correta (resumo/ranking/curva ABC), período vazio, validação de formato de data, isolamento entre tenants e RBAC.
- 6 testes e2e novos para Inventário cobrindo o fluxo completo (abrir → contar → finalizar → estoque ajustado), reconciliação contra saldo concorrente (movimentação durante a contagem), filtro de produto ativo/`trackStock`, transições de estado inválidas, isolamento entre tenants e RBAC.
- 5 testes e2e novos para Centro de custo/DRE cobrindo vínculo com conta financeira e agregação correta no DRE, centro de custo inexistente, desativação sem quebrar histórico, isolamento entre tenants e RBAC.
- 10 testes e2e novos para permissões granulares cobrindo override "allow"/"deny" nas duas direções, upsert (substituir regra existente), remoção volta ao default do papel, owner nunca é alvo, escopo por usuário e por tenant, RBAC de quem gerencia, subject fora da lista permitida rejeitado, e a invariante de "sempre existe ao menos um owner" intacta.

- **Cadastros (Clientes/Fornecedores):** o CRUD de `customers`/`suppliers` já existia por completo desde a Fase 1, mas sem nenhuma tela — cliente só entrava via API direta, o que ficou evidente ao testar o módulo de Compras (não dava pra escolher fornecedor sem ter cadastrado um antes). `/painel/cadastros` fecha essa lacuna com abas Clientes/Fornecedores (criar + listar + excluir), reaproveitando o mesmo padrão visual das outras páginas.
- **Relatórios/BI básico:** primeiro corte de BI usando dados que o PDV já gera (`sales`/`sale_items`), sem nenhuma infra nova — `GET /reports/vendas-resumo|produtos-ranking|curva-abc|vendedores-ranking`, todos aceitando `?from=&to=` (padrão: últimos 30 dias) e considerando só vendas com status `completed`. Curva ABC usa o corte clássico por receita acumulada (A até 80%, B até 95%, C o resto). RBAC via CASL (`Report`): `admin`/`owner`/`financeiro` leem, `operador_caixa` não acessa — mesma lógica de sensibilidade de dado financeiro do `FinanceEntry`. Frontend em `/painel/relatorios` com filtro de período, cards de resumo, ranking de vendedores e a curva ABC com badge de classe por produto.
- **Estoque avançado (inventário):** do escopo original de "Estoque avançado" do roadmap, só a parte que faz sentido pra uma loja única — contagem física de estoque (`stock_counts`/`stock_count_items`). "Múltiplos depósitos" e "transferência entre lojas" pressupõem multi-loja, que é item de Fase 3 (Expansão); implementar isso agora seria estado morto, mesmo raciocínio já aplicado ao "enviado" do Compras. Fluxo: abrir uma contagem tira uma foto de todos os produtos ativos com `trackStock`, o operador vai preenchendo a quantidade contada por item, e ao finalizar o sistema gera um ajuste (`StockService.applyMovement`, tipo `ajuste`) para cada item contado — recalculado contra o saldo **atual** do produto no momento da finalização (não o saldo congelado na abertura), pra não apagar uma venda ou recebimento de compra que aconteça no meio da contagem. Itens não contados ficam como estão, sem forçar contagem completa de tudo de uma vez. RBAC igual ao de `StockMovement`: `admin`/`owner` abrem/finalizam/cancelam, `financeiro` só lê, `operador_caixa` sem acesso. Frontend em `/painel/contagens`.
- **Financeiro avançado — centro de custo e DRE simplificado:** `cost_centers` é um cadastro simples (nome + ativo, sem exclusão definitiva) que `finance_entries` referencia opcionalmente. DRE simplificado (`GET /reports/dre`, mesmo módulo de Relatórios) soma receitas e despesas **já pagas** no período — regime de caixa, não de competência, porque não existe conciliação bancária real ainda; é mais honesto mostrar só o que efetivamente aconteceu do que fingir uma competência que o sistema não rastreia direito. Quebra o resultado por centro de custo, com um bucket "Sem centro de custo" pra contas sem classificação. RBAC: `admin`/`owner`/`financeiro` gerenciam centro de custo (mesmo grupo que já gerencia `FinanceEntry`), `operador_caixa` sem acesso. **Conciliação bancária ficou de fora deste corte** — importar/casar extrato OFX é alto esforço e incerteza sem uma conta bancária real conectada (mesmo raciocínio de adiar parceiro de pagamento/fiscal reais); revisitar quando houver essa integração.
- **Gestão de permissões granulares por usuário:** o RBAC continua sendo 4 papéis fixos (`owner`/`admin`/`financeiro`/`operador_caixa`) — isso não mudou. O que existe agora é uma camada de exceções pontuais **por usuário**, em cima do papel: `user_permission_overrides` (subject, action, effect `allow`/`deny`) que `AbilityFactory` aplica depois das regras do papel — no CASL, a última regra que casa com (action, subject) vence, então um override sempre tem prioridade sobre o default do papel, nas duas direções (conceder algo que o papel não dá, ou revogar algo que o papel daria). `owner` nunca é alvo de override (rejeitado com 400) — continua sendo a rede de segurança de todo o RBAC, igual à regra de "sempre existe ao menos um owner". Tabela sem RLS de propósito, mesmo grupo de `users`/`refresh_tokens` (identidade, filtro explícito por tenant/usuário, sem custo de transação extra na guarda de toda request autenticada). Gerenciado como sub-recurso de `User` (`/users/:userId/permission-overrides`) — só `admin`/`owner` mexem, mesma regra de "quem gerencia usuários". Frontend: painel expansível por usuário em `/painel/usuarios` (chips coloridos por exceção, adicionar/remover). Testado com o dobro do cuidado de qualquer módulo anterior por tocar o núcleo de autorização que todo o resto depende: precedência nas duas direções, escopo por usuário (não vaza entre usuários do mesmo tenant) e por tenant, RBAC de quem gerencia overrides, subjects fora da lista permitida rejeitados (sem escalar pra `all`/`Tenant`), e a suíte e2e inteira (75 testes) re-rodada no final pra garantir que nada regrediu.

Com isso, os cinco itens da Fase 2 (Compras, Estoque avançado, Financeiro avançado, Relatórios/BI, Gestão de usuários e permissões) estão implementados e testados.

**Revisão de segurança pós-Fase 2:** achado real de escalonamento de privilégio no módulo de permissões granulares — `update`/`create` no subject `User` (pensado só pra "gerenciar usuários") também destravava `PATCH /users/:id/role` e `POST /users/invite`, então um override aparentemente pontual concedido por um admin deixava o usuário se autopromover a `admin` ou convidar um novo `admin` de conta própria. Confirmado com um PoC e2e antes do fix. Correção: `UserAccess` virou um subject CASL à parte (convite + troca de papel + gestão de overrides), fora de `permissionSubjectSchema` — nunca pode ser concedido por override, só herdado do papel base `admin`/`owner`, mesmo tratamento que `all`/`Tenant` já tinham.

**Fase 3 (Expansão) — completa.** Todos os 5 módulos do roadmap entregues: **Fidelidade (CRM básico)**, **RH básico (comissão de vendedores** — "ponto"/controle de jornada deliberadamente fora de escopo, ver seção própria**)**, **Assinatura/billing**, **Multi-loja/franquias**, **Integração e-commerce/marketplaces (adapter)** e **App mobile de PDV offline-first** (PWA — fila local + sincronização automática + service worker de app shell, ver seção própria abaixo).

- **Fidelidade — pontos, resgate e histórico:** ledger de pontos por cliente (`loyalty_ledger_entries` — imutável, saldo é sempre `SUM(points)`, nunca uma coluna mutável) mais uma configuração por tenant (`loyalty_programs`: ativo, pontos por R$1 gasto, valor em centavos de 1 ponto no resgate). Ganho e resgate acontecem dentro da própria transação da venda (`SalesService.create`): resgate reduz o total da venda como um desconto adicional (validado contra o saldo atual do cliente — saldo insuficiente derruba a venda inteira, não fica resgate parcial), e o ganho é calculado sobre o total **líquido** já pago (depois de desconto e resgate), não sobre o subtotal bruto — assim resgatar pontos não "recicla" pontos sobre a parte que eles mesmos pagaram. Venda sem cliente identificado não ganha nem resgata pontos. Dobrou como cuidado de dinheiro de verdade (pontos são uma moeda): tudo em inteiro, nunca float, mesma disciplina de centavos já usada em vendas/financeiro. RBAC dobrado no subject `Customer` existente (não um subject novo) — `admin`/`owner` gerenciam a configuração, `financeiro`/`operador_caixa` só leem (o caixa precisa ver o saldo do cliente pra oferecer o resgate no PDV). Frontend: `/painel/fidelidade` (configuração do programa + consulta de cliente com saldo e histórico) e integração direta no PDV (seletor de cliente opcional, saldo exibido em tempo real, campo de resgate com preview do desconto).
- 10 testes e2e cobrindo ganho sobre total líquido, venda anônima não ganha, resgate reduz o total corretamente, saldo insuficiente derruba a venda inteira (nada de resgate parcial), resgate sem cliente selecionado é rejeitado, programa desativado bloqueia resgate mas não venda normal, histórico (ledger) na ordem certa, isolamento entre tenants (RLS) e RBAC de leitura vs. escrita da configuração.
- **Comissão de vendedores:** taxa padrão por tenant (`commission_settings`, em basis points — 500 = 5%, inteiro, mesma disciplina anti-float) com override individual opcional por vendedor (`seller_commission_rates`, único por `tenant_id`+`user_id`). Diferente de fidelidade, comissão **não é um ledger**: cada venda já registra `seller_id` desde o PDV (usado pelo ranking de vendedores existente), então o valor devido é calculado sob demanda agregando `sales` por vendedor no período — não precisa de consistência transacional com a venda nem de uma tabela de saldo, é puramente um relatório derivado. Extensão do módulo de Relatórios (`GET /reports/comissoes`) em vez de uma tela nova: agrega receita por vendedor, resolve a taxa (override se existir, senão o padrão do tenant) e calcula a comissão. RBAC no subject `Report` existente — `manage` (só `admin`/`owner`) pra configurar taxas, `read` (também `financeiro`) só pra ver o relatório. Frontend: `/painel/comissoes` (configuração da taxa padrão, gestão de taxas individuais por vendedor, relatório por período). "Ponto" (controle de ponto/frequência) fica **fora do escopo** por ora — é um domínio à parte (jornada, banco de horas, atestados) que não tem nenhuma peça já construída pra reaproveitar, diferente de comissão que nasceu quase pronta em cima do `seller_id` e do ranking já existentes; entra como item futuro de RH quando fizer sentido.
- 6 testes e2e cobrindo configuração default (ativo, taxa 0), aplicação da taxa padrão sobre a receita do vendedor, override individual sobrepondo o padrão e voltando ao padrão quando removido, RBAC (operador de caixa sem acesso, financeiro só lê, admin/owner configuram), validação do intervalo de taxa (0–10000 bps) e isolamento entre tenants (RLS).

**Assinatura/billing (cobrança recorrente dos próprios clientes do PCAARB):** o `tenants.status` já previa `trial`/`active`/`past_due`/`blocked`/`canceled` desde a Fase 0, mas nunca existiu um jeito de sair de `trial` — este módulo fecha esse ciclo. Preço fechado em `packages/shared/src/schemas/billing.ts` (`SUBSCRIPTION_PLAN_CATALOG` — ver [PRECOS-E-CUSTOS.md](PRECOS-E-CUSTOS.md) pro racional completo): Starter R$119, Profissional R$249, Multi-loja R$349+R$99/loja, Enterprise sob consulta (não assinável via checkout). Reaproveita a mesma interface `PaymentProvider`/adapter mock já usada no PDV (ver Fase 1) em vez de criar um segundo mecanismo de cobrança — cobrar a assinatura é conceitualmente a mesma operação de "cobrar um cartão", só que recorrente. `POST /billing/subscribe` serve três casos com um endpoint só: primeira assinatura, reativação (cancelada ou bloqueada por inadimplência) e troca de plano — **os três cobram o valor cheio na hora e reiniciam o ciclo de 30 dias** (sem proração — simplificação deliberada; ver "Revisão de segurança pós-multi-loja" abaixo pro porquê disso não ser mais opcional). Cron diário (`@nestjs/schedule`, mesmo padrão do job de expiração de trial) cobra ciclos vencidos: sucesso avança o período 30 dias, falha marca `past_due` com **5 dias de carência** (acesso mantido, tentativa repetida todo dia) antes de bloquear — e um tenant já bloqueado para de ser tentado sozinho, só reativa via `subscribe()` manual. Um decorator novo (`@BypassTenantStatus()`) libera os endpoints de billing do bloqueio global do `TenantStatusGuard` — sem isso um tenant bloqueado nunca conseguiria nem ver a própria fatura nem pagar pra reativar. Ações que comprometem dinheiro (assinar/cancelar) são restritas a `owner` via `@Roles('owner')` (guard que já existia pronto no código mas nunca tinha sido usado) — não um subject CASL, porque é decisão de dono do negócio, não gestão operacional. `subscriptions`/`subscription_invoices` deliberadamente **não têm RLS** — mesmo tratamento de `tenants`: são dado de plataforma sobre o tenant, não dado de negócio isolado, e o cron de cobrança precisa varrer todos os tenants de uma vez (RLS por sessão impediria isso). Frontend: `/painel/assinatura` (plano atual, trocar/cancelar, histórico de fatura) e `/precos` (página pública, sem necessidade de login).
- 9 testes e2e cobrindo: trial sem assinatura ainda, assinar cobra na hora e ativa o tenant, RBAC (só owner assina/cancela), troca de plano não gera cobrança duplicada, cancelar bloqueia o resto da API mas billing continua acessível pra reativar, renovação bem-sucedida avança o período, validação de plano inválido, e o ciclo completo de inadimplência (recusa não persiste nada / marca `past_due` com carência / só bloqueia depois da carência esgotar / para de tentar sozinho após bloquear).

**O que falta para vender de verdade** (não é mais código, é ação fora do repositório — ver conversa com o usuário de 2026-08-17): conta real no Pagar.me vinculada a CNPJ/banco (troca o adapter mock pelo real), conta em provedor fiscal real (sai do sandbox de NFC-e), revisão de advogado nos rascunhos de Termos de Uso/Privacidade antes de publicar, e domínio + hospedagem de produção.

**Multi-loja/franquias:** único item de Fase 3 que faltava para o plano Multi-loja (ver [PRECOS-E-CUSTOS.md](PRECOS-E-CUSTOS.md)) deixar de ser só uma linha na tabela de preços. Toda venda/caixa agora pertence a uma loja (`stores`, nova tabela com RLS) — tenant nasce com uma automaticamente no registro (mesmo nome da empresa), e **criar a 2ª exige o plano Multi-loja de verdade** (`StoresService.create` consulta `BillingService.getSubscription` — sem assinatura `multi_loja`/`enterprise` ativa, é 403), fazendo a integração entre billing e produto virar gate real, não só texto de marketing. Escopo desta fatia, deliberadamente contido:
- `cash_sessions`/`sales` ganharam `store_id` (a venda herda a loja do caixa que a originou — mesmo racional de denormalização de `sale_items`). Migração de dados: tenants existentes ganharam uma loja padrão via backfill (uma linha por tenant, nome = razão social) antes da coluna virar `NOT NULL` — sem isso `ALTER COLUMN ... SET NOT NULL` quebraria contra as linhas já existentes.
- **Estoque, financeiro, compras e cadastros continuam por tenant, não por loja** — mesma decisão já tomada na Fase 2 ("múltiplos depósitos e transferência entre lojas" ficou de fora do estoque avançado) — dividir estoque por loja é escopo maior, fica para uma fatia futura se/quando fizer sentido. Catálogo de produto e clientes/fornecedores são compartilhados entre as lojas de um tenant, o que já reflete como redes pequenas costumam operar.
- Permissão continua por papel a nível de tenant (RBAC de sempre), não por loja — um vendedor não fica restrito a "sua" loja nesta fatia. Subject CASL novo (`Store`): `admin`/`owner` gerenciam, `financeiro`/`operador_caixa` só leem (o caixa precisa listar lojas pra escolher onde abrir o caixa).
- Relatório consolidado (`GET /reports/lojas-ranking`, `/painel/relatorios`) é o valor real do plano — agrega vendas/receita por loja no período, mesmo formato do ranking de vendedores já existente.
- Frontend: `/painel/lojas` (criar/renomear/desativar — não permite desativar a única loja ativa), seletor de loja no PDV (só aparece quando há mais de uma loja — tenant de loja única não vê nenhuma UI a mais).
- Achado durante a implementação (bug de bootstrap, não falha de segurança): `TenantsService.registerWithOwner` roda fora de `runWithTenant` de propósito (não existe tenant ainda quando a transação começa) — como `stores` tem RLS, o insert da loja padrão dentro daquele registro falhava por falta de contexto de tenant na sessão. Corrigido setando `app.tenant_id` manualmente na mesma transação, mesmo mecanismo de `tenant-context.ts`, sem abrir uma transação nova.
- 9 testes e2e cobrindo: loja padrão criada no registro, bloqueio de 2ª loja sem plano, criação liberada com plano Multi-loja, RBAC, proteção contra desativar a única loja ativa, caixa recusa loja inativa, venda herda a loja do caixa, relatório consolidado agrega por loja corretamente, downgrade bloqueia loja extra na hora de usar (não só na hora de criar), e isolamento entre tenants (RLS).

**Revisão de segurança pós-multi-loja (2026-08-17):** achado real de integridade de billing — `BillingService.subscribe()` tinha um caminho de troca de plano em assinatura ativa que **não cobrava de novo**, e `StoresService.create()` só checava o plano na hora de criar a loja, nunca de novo depois. Combinados, um tenant podia assinar Multi-loja, criar N lojas extras, voltar pro Starter antes da renovação, e ficar operando todas as lojas extras pra sempre pagando preço de Starter — o valor real do plano Multi-loja (visão consolidada) vazava sem cobrança correspondente. Corrigido em duas frentes: (1) toda troca de plano agora cobra o valor cheio do novo plano na hora e reinicia o ciclo de 30 dias (sem proração — simplificação deliberada, documentada no código); (2) `StoresService.assertUsable()` reavalia o plano a cada abertura de caixa, não só na criação da loja — `CashSessionsService.open()` passou a chamar esse método em vez de só checar existência/ativação da loja, então uma loja extra criada num plano superior para de funcionar assim que o tenant faz downgrade (a loja mais antiga do tenant nunca é bloqueada, em nenhum plano). 2 testes de regressão novos provando o fechamento do buraco.

**Integração e-commerce/marketplaces (adapter):** fecha o penúltimo item arquitetural de Fase 3. Mesmo padrão de `PaymentProvider`/`FiscalProvider` (Fase 1) — uma interface (`MarketplaceProvider`, em `apps/api/src/modules/marketplace/`) com duas operações (`syncProduct`, `fetchNewOrders`) e um adapter mock por trás; trocar por um canal real (Shopify, Mercado Livre) é escrever um novo adapter, não mexer no resto do sistema. Não existe conta/credencial real ainda, então o mock é honesto sobre isso: sincronizar produto sempre funciona (devolve um id externo fabricado), e não há pedidos pendentes (`fetchNewOrders` devolve `[]`) — mesmo racional do `MockPaymentProvider` sempre aprovar. Três tabelas novas com RLS: `marketplace_channels` (canal conectado por tenant), `marketplace_listings` (vínculo produto↔canal, idempotente por `channelId+productId`) e `marketplace_orders`/`marketplace_order_items` (pedido importado, idempotente por `channelId+externalOrderId`).
- Decisão deliberada de escopo: um pedido importado **não vira uma `Sale` de PDV** — `sales` exige `cashSessionId` (caixa físico aberto), o que não existe pra um pedido feito de madrugada num marketplace. O que precisa ficar consistente entre os dois canais é o **estoque compartilhado**: importar um pedido aplica `StockService.applyMovement` (mesmo código usado pelo PDV) direto, sem fingir que é uma venda de balcão. Faturamento/relatório consolidado de vendas online fica fora do escopo desta fatia — mesmo padrão de adiamento já usado em conciliação bancária e "múltiplos depósitos".
- Duas garantias de correção, mesmo cuidado do que está planejado pro PDV offline (ver roadmap): **idempotência** (reprocessar a mesma lista de pedidos, por retry ou por chamar de novo, nunca abate estoque duas vezes — `onConflictDoNothing` na unique de `channelId+externalOrderId`) e **tudo-ou-nada por pedido** (se qualquer item do pedido não resolve pra um produto sincronizado, ativo, com estoque suficiente, o pedido inteiro vira `needs_attention` com o motivo registrado — nenhum item dele é aplicado, nunca uma correção parcial silenciosa).
- CASL: subject novo `Integration`, restrito a `admin`/`owner` (configurar canal externo não é operação do dia a dia do caixa/financeiro, diferente de `Store`).
- Frontend: `/painel/integracoes` — conectar canal (sandbox), tabela de produtos com status de sincronização por canal, tabela de pedidos importados com o motivo exposto quando `needs_attention`.
- 6 testes e2e cobrindo: CRUD de canal, RBAC, sincronização de produto idempotente, sincronizar em canal inativo é rejeitado, canal sem pedidos devolve lista vazia (comportamento real do sandbox), e — com um adapter de teste fabricado via `overrideProvider` (mesmo padrão usado pra testar recusa de pagamento/fiscal fora do ar) — importação com produto mapeado e estoque suficiente, produto não mapeado, estoque insuficiente, e replay não reaplica nada (idempotência) nem mexe no estoque de novo.

**PDV offline (fila local + sincronização automática + app shell) — último item de Fase 3, completo:** construído como PWA (service worker cacheando o app shell) em cima do `/painel/pdv` existente, não um app nativo — decisão de arquitetura documentada na memória do agente. Fatia 1 (perda de conexão momentânea com o operador já na tela do PDV) foi entregue primeiro; fatia 2 (sobreviver a um F5 100% offline) foi deliberadamente adiada naquele momento e implementada nesta sessão seguinte.
- **Service worker sem manifesto de precache** (`apps/web/public/sw.js`, JS puro, sem dependência nova): deliberadamente **não** usa o approach do `next-pwa`/Workbox precache manifest (lista de hashes de build gerada em build time) — nomes de arquivo do Next.js mudam a cada deploy, e essa lista vira lixo obsoleto apontando pra URLs que não existem mais no próximo deploy (o "footgun" de versionamento identificado quando a fatia 2 foi adiada). Em vez disso, cache só-em-runtime: documento HTML é sempre buscado network-first (online nunca serve algo obsoleto, e o cache se autoatualiza a cada visita, sem precisar bumpar versão a cada deploy) com fallback pro cache só quando o fetch falha de verdade; assets estáticos com hash de conteúdo no nome (`_next/static/*`) são cache-first (uma URL com hash nunca muda de conteúdo). Só intercepta `GET` de mesma origem — mutação (POST/PATCH/DELETE) e chamada pra API (outra origem) passam direto, nunca arriscando servir uma resposta cacheada de uma venda. Avaliado usar Serwist (a alternativa que o próprio guia de PWA do Next.js recomenda para Turbopack) e descartado por risco de compatibilidade: este projeto está em Next.js 16 recém-lançado, e o hand-rolled evita depender de um plugin de build de terceiros ainda se adaptando a essa versão.
- **Cache do TanStack Query persistido em localStorage** (`apps/web/src/app/providers.tsx`, `@tanstack/react-query-persist-client`): sem isso, o app shell carregava offline mas ficava preso esperando rede pros dados (produto, caixa aberto) que nunca vinham. Allowlist fechada de chaves (`users`, `current-cash-session`, `products`, `customers`, `loyalty-program`) — só o que o PDV precisa pra funcionar offline, não lixo de outras telas.
- **Rascunho do carrinho em andamento também sobrevive a um F5 offline** (`localStorage`, escopado por tenant): um reload no meio de uma venda (item já selecionado, forma de pagamento já escolhida) não perde o que o operador já montou — sem isso, a sobrevivência a reload do app shell seria inútil pra esse caso, o mais comum de acontecer offline.
- **Bug pré-existente encontrado e corrigido no caminho** (não introduzido nesta sessão, mas bloqueava a própria verificação da fatia 2): `useAccessToken` tinha uma corrida de hidratação real — `getServerSnapshot()` retornava `null` (mesmo valor de "confirmei que não tem token"), e o efeito de redirecionamento do `/painel/layout.tsx` disparava nessa primeira renderização (que sempre usa o snapshot do servidor, mesmo no cliente, só pra bater com o HTML do SSR) **antes** do `useSyncExternalStore` corrigir pro valor real do `localStorage` — chutando pra fora do sistema um usuário logado em **todo** F5/aba nova de qualquer página de `/painel/*`, online ou offline. Reproduzido e confirmado ao vivo via Playwright antes do fix. Corrigido trocando o valor de "ainda não sei" de `null` pra `undefined` — um terceiro estado que o efeito de redirecionamento (que checa `=== null`, não `!accessToken`) sabe distinguir de "confirmei que está deslogado".
- **Idempotência de verdade, não só client-side:** `sales` ganhou `client_sale_id` (uuid gerado no navegador com `crypto.randomUUID()` no momento de "Finalizar venda", único por `tenant_id`), e `SalesService.create` passou a checar essa chave **antes** até de exigir caixa aberto — porque uma venda enfileirada offline pode ser reenviada depois que o caixa que a originou já fechou, e ela precisa voltar a mesma venda já concluída, não ser barrada de novo. O insert usa `onConflictDoNothing` na unique de `(tenant_id, client_sale_id)` como rede de segurança contra duas tentativas em voo ao mesmo tempo (retry de rede + fila do dispositivo, por exemplo): o Postgres serializa os dois inserts, quem perde busca a venda que a outra já criou — nenhum efeito colateral (cobrança, estoque, pontos) roda duas vezes. Testado inclusive com duas requisições **de verdade concorrentes** via `Promise.all` (não só sequenciais), não só via e2e mas com verificação manual em navegador real usando `page.context().setOffline(true)`.
- **Fila local em IndexedDB** (`apps/web/src/lib/offline-sale-queue.ts`, API nativa do navegador, nenhuma dependência nova): quando o PDV finaliza uma venda sem conexão — detectado tanto por `navigator.onLine` quanto por um `fetch()` que falha de verdade no meio da tentativa — a venda vai pra fila local em vez de ser perdida ou travar a tela. Ao reconectar (evento `online`, mais uma tentativa ao carregar a página), cada venda pendente é reenviada com a mesma `clientSaleId`; sucesso remove da fila, recusa de verdade do servidor (estoque insuficiente, produto desativado nesse meio tempo, etc.) marca a venda como "precisa de atenção" com o motivo exposto na tela e um botão de descartar — nunca reaplica sozinha pra sempre, nunca some silenciosamente. Testado ao vivo simulando os três casos: sincroniza normal, fica pendente enquanto realmente offline, e cai em "precisa de atenção" quando o produto é desativado enquanto a venda estava na fila.
- **Gotcha real descoberto na implementação, documentado em comentário no código:** o `networkMode` padrão do TanStack Query (`'online'`) **pausa a mutation inteira** enquanto `navigator.onLine` é falso — nunca chega a chamar a função da mutation. Isso anularia completamente o enfileiramento (a mutation nunca rodaria pra decidir "estou offline, vou enfileirar"; o botão ficaria girando pra sempre até a conexão voltar sozinha). A mutation de criar venda e a query que lê a fila local (`offlineQueueQuery`) precisaram de `networkMode: 'always'` — a lógica de conectividade já é tratada manualmente dentro delas, não pode depender do controle de rede do react-query por cima.
- Caixa precisa já estar aberto **antes** de ficar offline — abrir caixa em si não funciona sem rede (decisão deliberada, documentada: não vale a pena estender o enfileiramento pra cobrir abertura de caixa nesta fatia). Preços/estoque exibidos offline são os últimos conhecidos (cache do React Query), com um aviso na tela indicando isso.
- Sem testes de frontend automatizados (não existe framework de teste no `apps/web` ainda) — verificação foi 100% via Playwright ao vivo, incluindo reload 100% offline real via CDP (`page.context().setOffline(true)` + reload de página inteira), não é mockado. Achado incidental da verificação: `context.setOffline(true)` do Playwright bloqueia rede de verdade mas **não** vira `navigator.onLine = false` — validou na prática que o app não pode confiar só nesse sinal (é exatamente por isso que a mutation de venda também trata falha de `fetch()` diretamente, não só o valor de `isOnline`). O fluxo "precisa de atenção" também foi validado sem querer: uma venda enfileirada offline pra um produto com saldo zero voltou do reconnect com a recusa real do servidor ("Estoque insuficiente") em vez de sumir ou reaplicar.
- Ainda deferido: página dedicada de histórico/gestão da fila offline fora do PDV (hoje só aparece inline na própria tela de venda).

**Menu do topbar reorganizado em dropdowns:** os 14 links de navegação numa única linha passaram a obrigar rolagem lateral em telas normais (não é mais um problema de tela pequena — 14 itens simplesmente não cabem). Painel/PDV continuam soltos (telas mais usadas no dia a dia); o resto virou 4 dropdowns por área (Operação, Clientes, Financeiro, Configurações) — 6 itens no topo, cabe sem rolar em qualquer largura razoável (testado até 1024px). Estado de qual dropdown está aberto reseta ao trocar de rota via `key={pathname}` remontando o componente do menu (não `useEffect`/comparação de ref durante o render — ambos proibidos pelas regras de hooks deste projeto, ver comentário no código).

**Fase 4 (Avançado/Enterprise) — iniciada. Primeiro item: API pública com chaves de API.** Fase 3 fechou o roadmap original, mas o objetivo real do projeto é venda/aquisição (ver memória do agente), não crescer como SaaS brasileiro — então a pergunta de "o que construir depois" foi reavaliada sob essa ótica, não só seguindo a ordem do roadmap. "API-first" é um dos 5 diferenciais pretendidos desde o documento de visão original (seção 3), e Swagger/OpenAPI já existia (`/api/docs`) documentando toda a API — mas não tinha um jeito de um sistema de terceiro se autenticar programaticamente: a única via era um JWT de usuário (curta duração, 15min, nascida de login interativo). Chave de API fecha essa lacuna.
- **Reaproveita 100% do CASL existente, zero mecanismo de permissão novo:** uma chave de API não tem um sistema de permissão próprio — ela "é" uma conta de serviço com um papel normal (`owner`/`admin`/`financeiro`/`operador_caixa`, o criador escolhe), sujeita exatamente às mesmas regras de RBAC que um usuário logado. Tecnicamente, a conta de serviço é uma linha de verdade em `users` (`is_service_account: true`, senha aleatória nunca revelada, fora da listagem humana de usuários) — não um principal sintético — porque várias tabelas têm FK `NOT NULL` pra `users.id` (`sales.seller_id`, etc.); assim toda ação feita via chave satisfaz essas FKs de graça, sem precisar auditar/alterar cada uma.
- **`JwtAuthGuard` (global, único ponto de entrada de autenticação) passou a aceitar chave de API além de JWT**, reconhecida pelo prefixo do token (`pcaarb_live_...`, não tenta parsear como JWT primeiro). Quando valida, monta um `request.user` no exato formato que a estratégia JWT produziria (`{sub, tenantId, role}`) — então `RolesGuard`/`TenantStatusGuard`/`AbilityGuard`/`CurrentUser`/todo controller continuam funcionando sem nenhuma mudança, sem essa alternativa de autenticação vazar pra nenhuma outra camada da stack.
- **Segredo nunca fica recuperável depois da criação:** só o hash SHA-256 é persistido (não bcrypt — a chave já nasce com 192 bits de entropia aleatória, não é senha humana adivinhável, mesmo racional de token de API do GitHub/Stripe); a resposta de criação devolve a chave crua **uma única vez**, nunca mais. Revogação é irreversível (sem "reativar"); expiração opcional é checada em toda autenticação, não só na criação.
- **Escalonamento de privilégio fechado no design, não como patch depois:** só quem já tem a ability `create`/`Integration` (admin/owner) cria chaves — e um admin (não-owner) não consegue mintar uma chave com papel `owner`, mesma regra que já existia pra convidar um usuário como owner (`UsersService.inviteUser`). Papel de quem está criando é sempre relido do banco, não confia no papel do JWT (pode estar desatualizado).
- Mesmo subject CASL de sempre (`Integration`, admin/owner-only) — chave de API é uma forma de configurar integração externa, não mereceu um subject novo. `api_keys` deliberadamente **sem RLS**, mesmo grupo de `users`/`tenants`/`refresh_tokens`: validar uma chave acontece antes de qualquer contexto de tenant existir (o guard só descobre o tenant depois de achar a chave pelo hash), então RLS ali bloquearia a própria autenticação — isolamento nas rotas de gestão vem de filtro explícito de `tenant_id`, mesmo padrão de `UsersService.listByTenant`.
- Frontend: seção "Chaves de API" em `/painel/integracoes` (mesma tela do marketplace, mesmo subject) — criar (nome + papel + expiração opcional), banner de aviso mostrando a chave crua uma única vez com botão de copiar, listagem (prefixo, papel, último uso, status) e revogar.
- 11 testes e2e cobrindo: criação com exposição única do segredo cru (nunca persistido em texto puro, confirmado direto no banco), listagem nunca expõe segredo/hash, revogar impede autenticação e revogar de novo é rejeitado, chave expirada é rejeitada, criar já expirada é rejeitado, uma chave `operador_caixa` vende mas não gerencia produtos (CASL de verdade, não bypass), RBAC de quem gerencia chaves, admin não-owner não consegue criar chave de papel owner (owner consegue), conta de serviço nunca aparece na listagem de usuários, isolamento entre tenants, e token com formato de chave de API mas inválido é rejeitado com 401 (não 403 — é falha de autenticação, não de autorização).

**Exportação de dados para o contador (CSV):** o item de roadmap "integrações contábeis (SPED fiscal/contábil)" foi deliberadamente **não** implementado como SPED de verdade — emitir um arquivo de escrituração fiscal oficial exige validação de quem entende a legislação tributária caso a caso (varia por estado/regime, mesmo risco identificado em [docs/01](docs/01-visao-geral-e-roadmap.md) para emissão fiscal), e não existe esse tipo de revisão disponível agora. Em vez disso, `GET /reports/exportar/vendas.csv` e `GET /reports/exportar/financeiro.csv` (mesmo subject CASL `Report`, mesmos filtros `?from=&to=` dos outros relatórios) exportam o dado bruto — vendas com forma de pagamento e status/chave da NFC-e, contas a pagar/receber do período — num CSV que qualquer contador importa na ferramenta dele. Resolve a mesma dor real ("meu contador precisa desses dados") sem o risco de compliance de gerar um arquivo formalmente errado.
- CSV usa `;` como separador e BOM UTF-8 (`apps/api/src/common/utils/csv.ts`) — abre corretamente no Excel em pt-BR, que não reconhece `,` nem UTF-8 sem BOM por padrão.
- **Bug real encontrado na verificação ao vivo, não nos testes automatizados:** o download funcionava via `curl`/Supertest (mesma origem, sem CORS) mas o front sempre baixava com o nome genérico `exportacao.csv` em vez do nome real (`vendas_2026-08-01_a_2026-08-18.csv`) — porque `fetch()` cross-origin (API em `:3001`, front em `:3000`) só expõe ao JavaScript a lista "segura" de response headers por padrão, e `Content-Disposition` não está nela. Corrigido com `exposedHeaders: ['Content-Disposition']` no `enableCors` (extraído para `apps/api/src/cors.config.ts`, importado tanto por `main.ts` quanto pelo e2e novo, pra o teste validar a configuração real usada em produção, não uma cópia que pode divergir). Reforça a lição já registrada nesta sessão (`useAccessToken`): comportamento de rede/hidratação real só se confirma testando ao vivo, os testes automatizados (que rodam same-process, sem CORS de verdade) não pegam essa classe de bug.
- Frontend: dois botões "Exportar vendas"/"Exportar financeiro" em `/painel/relatorios`, reaproveitando o mesmo filtro de período da tela. `apiDownload()` novo em `api-client.ts` (o `apiFetch` existente sempre faz `.json()`, incompatível com blob) — lê o nome do arquivo do header `Content-Disposition` da resposta e dispara o download via link temporário.
- 4 testes e2e novos: conteúdo/cabeçalho do CSV de vendas (formas de pagamento formatadas, status fiscal), CSV financeiro filtrado por período, RBAC (operador de caixa não acessa nenhum dos dois exports — mesma regra de `Report`), e o header CORS exposto de verdade num request com `Origin` cross-origin simulado.

**BI avançado — sugestão de reposição de estoque e de precificação:** segundo item de "BI avançado" do roadmap Fase 4 (o primeiro era o item de exportação para contador acima). Deliberadamente **heurística, não um modelo de "IA"**: `GET /reports/reposicao` estima demanda por média móvel simples (quantidade vendida no período ÷ dias do período) — sem sazonalidade/tendência — e projeta `estoque atual ÷ venda média diária` pra prever em quantos dias o produto esgota, sugerindo quantidade de compra pra cobrir um período-alvo (`coverageDays`, padrão 14 dias); `GET /reports/precificacao` sugere preço por margem-alvo (`custo ÷ (1 − margem)`, padrão 30%) e sinaliza produto vendido abaixo do custo. Nomeado honestamente na UI como "estimativa"/"heurística", nunca como "previsão de IA" — é reaproveitamento direto do dado que `sales`/`sale_items`/`products` já têm, zero infra nova.
- Filtra ruído deliberadamente: produto sem venda no período e com saldo saudável não aparece na sugestão de reposição (não há dado pra sugerir nada); produto com saldo zerado sempre aparece, mesmo sem histórico de venda, porque "está zerado" já é acionável por si. Precificação só considera produto com custo cadastrado.
- Mesmo subject CASL `Report` de todos os outros relatórios (nenhum mecanismo novo).
- Frontend: duas novas seções em `/painel/relatorios` (tabela de reposição com badge "Atenção"/"OK"; tabela de precificação com input de margem-alvo e badge quando o preço está abaixo do custo).
- 4 testes e2e novos: matemática da estimativa de reposição (inclusive o filtro de ruído — produto nunca vendido com saldo saudável fica de fora), cálculo de margem/preço sugerido (inclusive produto sem custo fica de fora), RBAC, e isolamento entre tenants (RLS).
- **Achado real na verificação ao vivo, não relacionado à feature em si:** as duas seções novas simplesmente não apareciam na página, sem nenhum erro no console — o service worker do app shell (`public/sw.js`, ver seção do PDV offline) registrava incondicionalmente mesmo em `next dev`, e seu cache-first pra `_next/static/*` (seguro em produção, onde o nome do chunk é hash de conteúdo de verdade — confirmado inspecionando `.next/static/chunks/` depois de um `next build`) **não é seguro no Turbopack em modo dev**, onde a URL do chunk não muda de forma confiável entre restarts do dev server mesmo com conteúdo diferente. Resultado: o navegador continuava servindo JS de uma versão anterior da página, indefinidamente, sem nenhum sinal de erro. Corrigido registrando o service worker só quando `NODE_ENV === 'production'` (`apps/web/src/app/sw-register.tsx`) — sem efeito no comportamento de produção (continua registrando normalmente), mas fecha essa armadilha pra qualquer verificação ao vivo futura em modo dev. **Revisão de segurança (2026-08-18) — escalonamento de privilégio via chave de API:** rodada dedicada cobrindo os módulos acumulados desde a revisão anterior (marketplace, PDV offline, exportação CSV, BI avançado, impressão de cupom/histórico de vendas/pedido de compra). Achado real de alta severidade: `POST /api-keys` (módulo de chaves de API, adicionado há algumas iterações) é protegido pelo subject CASL `'Integration'` — o mesmo subject usado pelo módulo de marketplace — e esse subject **é** concedível por override pontual (ao contrário de `UserAccess`, que já era deliberadamente excluído por esse motivo desde uma correção anterior). Um admin concedendo a um `financeiro`/`operador_caixa` um override aparentemente inócuo como "deixa essa pessoa configurar a integração do marketplace" (`{subject:'Integration', action:'create', effect:'allow'}`) sem querer destravava `POST /api-keys` pra esse usuário — e o único guard existente em `ApiKeysService.create()` bloqueava só `role:'owner'` por quem não é owner, nada impedia pedir `role:'admin'`. Resultado: um funcionário de financeiro/caixa conseguia mintar uma credencial de API durável com abilities CASL equivalentes a admin do tenant inteiro.
- Corrigido em duas camadas: (1) `'Integration'` removido de `permissionSubjectSchema` (`packages/shared`), mesmo tratamento já dado a `'UserAccess'` — agora só o papel base admin/owner alcança `POST /api-keys`, nunca por override pontual; (2) `ApiKeysService.create()` trocou o check de "só bloqueia owner" por uma comparação de hierarquia de papel (`apps/api/src/modules/api-keys/role-rank.ts`, com testes unitários dedicados) que nunca deixa mintar uma chave com papel maior que o de quem está criando — defesa em profundidade, pra sobreviver mesmo se algum subject voltar a ficar overridable por engano no futuro.
- Achado e verificado pelo processo de 2 etapas (agente identifica → agente independente confirma end-to-end lendo o código, sem confiar só na descrição) antes de qualquer correção — confiança 9/10 na verificação. Teste de regressão novo em `permissoes-granulares.e2e-spec.ts` (override de `'Integration'` agora rejeitado com 400, ao lado dos já existentes pra `'all'`/`'Tenant'`/`'UserAccess'`); suíte completa (139 testes e2e + 38 unitários, incluindo os 4 novos de `role-rank.spec.ts`) verde depois da correção.

**Revisão de segurança ampla (2026-08-18) — pedido explícito do usuário, não escopada só no diff:** primeira rodada olhando o sistema inteiro (todos os 22 controllers, dependências, autenticação) em vez de só as mudanças recentes — pedido específico cobrindo força bruta, XSS, injeção, dependências vulneráveis e informação exposta via DevTools/resposta da API. Três achados reais, todos corrigidos:
1. **`drizzle-orm@0.38.2` com CVE conhecida (SQL injection via identificador mal escapado em `escapeName()`).** `pnpm audit` acusou 45 vulnerabilidades no total, quase todas em dependências de build/dev (`@nestjs/cli`, `vitest`) nunca expostas em produção — essa foi a única em severidade alta+ **e** na árvore de dependência de runtime de verdade. O aviso só afeta quem passa entrada não confiável pra `sql.identifier()`/`.as()` dinâmico/ordenação por nome de coluna vindo de request — busquei esse padrão exato no projeto inteiro e não existe: todo `orderBy`/`.as()` usa referência estática do schema. **Não explorável hoje**, mas corrigido mesmo assim (`^0.45.2`, a versão estável atual) como defesa em profundidade — testado num branch descartável (typecheck + 139 e2e + 38 unitários) antes de aplicar de verdade, sem quebra apesar do salto de versão.
2. **Vazamento de e-mail cadastrado por tempo de resposta no login (`AuthService.login`).** `bcrypt.compare` (custo 12, dezenas de ms) só rodava quando o usuário existia; "e-mail não encontrado" respondia na velocidade de uma busca indexada (poucos ms). Mensagem de erro idêntica nos dois casos, mas o *tempo* de resposta já é um oráculo clássico (CWE-208) pra descobrir quais e-mails têm conta — útil pra montar lista de phishing/credential-stuffing direcionado, mesmo sem vazar senha nenhuma. Corrigido com a mitigação padrão: um hash fixo (`DUMMY_PASSWORD_HASH`) calculado uma vez no boot, e `bcrypt.compare` passa a rodar sempre — contra o hash real se o usuário existe, contra o dummy se não — igualando o tempo dos dois caminhos. O mesmo padrão existe em `UsersService.acceptInvite` (comparação de token de convite), mas ali não é acionável: está atrás de um `inviteId` (UUID) impossível de adivinhar primeiro, e este projeto já trata UUID como confiavelmente não-adivinhável em outros pontos — não haveria como alcançar o ramo de tempo diferente sem já ter adivinhado o UUID, o que nenhum ataque de tempo torna viável.
3. **`GET /billing/subscription` e `GET /billing/invoices` sem nenhuma restrição de papel** — qualquer membro autenticado do tenant, inclusive `operador_caixa`, conseguia ver plano/preço/histórico de cobrança. Causa raiz: `RolesGuard` e `AbilityGuard` são deliberadamente "no-op" quando uma rota não declara `@Roles()`/`@CheckAbilities()` nenhum (design intencional documentado no próprio guard) — o que significa que a autorização de cada rota nova é opt-in, sem checagem estática; esquecer o decorator deixa o endpoint aberto por omissão, não por escolha. Auditei os 22 controllers da API inteira contra exatamente essa lacuna (script comparando cada `@Get/@Post/@Patch/@Put/@Delete` contra `@Public()`/`@CheckAbilities`/`@Roles`) — só esses 2 endpoints estavam genuinamente sem guarda (`GET /users/me` também acusou na primeira passada, mas é exceção conhecida e já documentada: ler a própria identidade não é gestão de usuário). **Achado sinalizado explicitamente como decisão de produto, não só corrigido calado**: um teste e2e já existente tinha um comentário afirmando "leitura continua liberada pra qualquer papel do tenant" — ou seja, isso pode ter sido decisão deliberada de uma sessão anterior, não um buraco acidental. Corrigido mesmo assim (`@Roles('owner', 'admin')` nos dois, consistente com o resto do próprio arquivo já tratar billing como "decisão de dono do negócio, não gestão operacional", e com `FinanceEntry` já ser restrito do mesmo jeito), teste atualizado pra refletir o novo comportamento, e a página `/painel/assinatura` ganhou uma checagem equivalente no front (não dispara mais as consultas fadadas a 403 pra papel sem permissão, mostra uma mensagem explícita em vez de deixar a busca falhar silenciosamente). **Confirmado pelo usuário em 2026-08-18**: restrição a dono/admin é o comportamento desejado, não era decisão anterior deliberada de deixar aberto.
- Também varrido e sem achados: headers de segurança (`helmet()` já ativo), rate limiting/força bruta (login já limitado a 5/min, cadastro/convite a 20/min, default global 100/min — nada disso é desta sessão), política de senha (mínimo 10 caracteres + maiúscula/minúscula/número, no cadastro e na aceitação de convite), higiene de JWT (segredos de access/refresh separados, validados em ≥32 caracteres no boot, TTL de 15min/7dias), revogação de refresh token no logout, XSS (zero `dangerouslySetInnerHTML`/`innerHTML`/`eval` em todo o frontend e no service worker), injeção de HTML no e-mail de convite (já escapado por um `escapeHtml()` dedicado, de sessão anterior), resposta da API nunca vazando `passwordHash`/`tokenHash`/chave de API crua, tratamento de erro (mensagem genérica pro cliente em exceção não tratada, stack trace só no log do servidor), validação Zod sem vazar detalhe interno, CORS restrito a uma origem, zero segredo hardcoded no código, `.env`/`.env.local` corretamente fora do git, sem source map em build de produção, zero superfície de injeção SQL/comando/path traversal, ordem de guards global correta. Não existe funcionalidade de "esqueci minha senha" — não é vulnerabilidade (nada pra atacar), mas fica anotado como lacuna de produto real pra uma iteração futura. Suíte completa (139 e2e + 38 unitários) e build verdes com todas as correções juntas.

**Devolução/estorno de venda (2026-08-19) — maior lacuna funcional do sistema, fechada.** Um diagnóstico de prontidão pra venda/aquisição (2026-08-18, ver memória do agente) apontou que nenhuma venda, uma vez lançada, podia ser desfeita — `sales.status` já previa o valor `'canceled'` desde a Fase 1, mas nada no código jamais o atribuía. Primeiro item de um plano de fechamento de lacunas revisado e aprovado pelo usuário antes de qualquer código (ver plano em `.claude/plans`), priorizado por ser o gap que qualquer comprador testando o produto notaria primeiro.
- **Tudo-ou-nada por devolução, não por linha:** se qualquer item pedido excede o saldo ainda não devolvido daquela linha (`sale_return_items` de devoluções anteriores, somado), a devolução inteira é rejeitada antes de gravar qualquer coisa — nunca fica parcialmente aplicada. Diferente do padrão `needs_attention` do marketplace (lote não-supervisionado, onde persistir o que falhou faz sentido), devolução é uma ação interativa de um operador — um erro de validação vira uma resposta clara na hora, não um registro pra ele caçar depois.
- **`needs_attention` reservado pra casos onde dinheiro/estoque já foram aplicados corretamente, mas algo secundário precisa de atenção humana:** (1) venda original com resgate de pontos de fidelidade — devolver os pontos resgatados E o dinheiro é uma decisão de negócio ambígua (dobra o benefício ao cliente?), então a reversão de pontos fica de fora deliberadamente nesse caso e a devolução é sinalizada, mas estoque/caixa aplicam normal; (2) cancelamento de NFC-e falha no provedor fiscal (mockado) — não é motivo pra travar a reversão de dinheiro/estoque, só fica visível que a parte fiscal precisa de reemissão manual depois.
- **Rateio proporcional, não preço de tabela:** se a venda teve desconto ou resgate de pontos, cada linha devolvida usa `unitPriceCents × quantidade × (sale.totalCents / sale.subtotalCents)` — devolve a fração do que o cliente pagou de fato, nunca mais do que isso.
- **Reembolso por três vias**, todas reaproveitando infraestrutura existente em vez de inventar um mecanismo de pagamento novo: dinheiro exige caixa aberto do operador que está processando agora (mesma checagem de `getCurrentOpenSession` da venda) e gera um `cash_movements` tipo novo (`estorno`, ao lado de `sangria`/`suprimento`); cartão/Pix chama `PaymentProvider.refund()` (método novo na mesma interface do `charge()`, mock aprova sempre) — recusa derruba a transação inteira, nada fica "meio estornado"; "outro" (troca, crédito combinado à parte) só registra, sem efeito colateral automático.
- **Fiscal:** cancelamento de NFC-e (`FiscalProvider.cancelNFCe()`, novo método espelhando `issueNFCe()`, novo status `canceled` em `fiscal_document_status`) só é tentado quando a devolução fecha 100% da venda — devolução parcial não mexe no documento fiscal (nota complementar de devolução é um fluxo fiscal diferente, fora de escopo). Sale vira `status: 'canceled'` no mesmo caso; devolução parcial mantém `'completed'`.
- Duas tabelas novas com RLS (`sale_returns`, `sale_return_items`, mesmo padrão de `sale_items` — item denormaliza `tenant_id`), subject CASL novo `SaleReturn` (mesma sensibilidade de `Sale`: `operador_caixa` cria/lê, `financeiro` só lê, `admin`/`owner` gerenciam) em ambos os enums (`ability.factory.ts` e `permissionSubjectSchema`, mesma convenção dual de todo subject existente).
- Frontend: ação "Devolver" em `/painel/vendas` (só aparece em venda `completed`) abre um formulário inline por linha de item com o saldo restante calculado a partir das devoluções já registradas, motivo e meio de reembolso; devoluções anteriores da venda ficam listadas com valor e status.
- 9 testes e2e cobrindo: devolução total (estoque restaurado, venda cancelada, NFC-e cancelada, movimento de caixa registrado), devolução parcial (venda continua completed, fiscal intocado), rateio proporcional com desconto, quantidade excedente rejeitada (nada aplicado), reembolso em dinheiro sem caixa aberto rejeitado, venda com resgate de pontos fica `needs_attention` só na fidelidade mas aplica o resto, estorno em cartão/Pix chamando o provedor e recusando quando a venda não tem pagamento não-dinheiro pra estornar, mais os dois testes de regressão da revisão de segurança abaixo. Verificado também ao vivo via Playwright: venda de 2 unidades por Pix, devolução parcial de 1 unidade via estorno de pagamento, conferindo estoque restaurado (9, não 10 nem 8) e o card de devolução aparecendo na tela com o valor e status corretos.

**Revisão de segurança dedicada pós-devolução (2026-08-19)** — obrigatória por mexer em dinheiro/estoque/fiscal, feita antes do commit, não depois. Metodologia de 2 etapas (agente identifica → agentes independentes verificam cada achado sem confiar na descrição, só lendo o código): 2 achados brutos, 1 sobreviveu ao filtro de confiança (≥8/10).
1. **Alta severidade, confirmado — duas linhas pedindo o mesmo item na mesma requisição de devolução dobravam (ou multiplicavam por N) o reembolso/estoque/pontos.** `alreadyReturnedByItem` (saldo já devolvido em devoluções *anteriores*) era comparado contra cada linha da requisição *atual* isoladamente, nunca contra a soma das linhas da própria requisição — então `items: [{item X, qtd 5}, {item X, qtd 5}]` numa venda que só vendeu 5 unidades passava nas duas checagens independentes (`0+5>5` falso duas vezes) e a devolução inteira aplicava o dobro: dois créditos de estoque, um reembolso em dobro no caixa/gateway. Sem corrida nenhuma envolvida — 100% determinístico numa única requisição de um `operador_caixa` comum, o papel de mais baixo privilégio que já tem `create`/`SaleReturn` legitimamente. Corrigido agregando `input.items` por `saleItemId` (soma as quantidades pedidas) **antes** de validar contra o saldo e antes de gerar as linhas que alimentam estoque/caixa/pagamento/persistência — mesma lógica de agregação que já existia só para devoluções anteriores, agora aplicada também dentro da própria requisição. Teste de regressão novo prova as duas metades do fix: quantidade agregada que excede o saldo é rejeitada (nada aplicado), e quantidade agregada dentro do saldo vira uma única linha combinada (não duas aplicadas em paralelo).
2. **Achado secundário, não confirmado como vulnerabilidade de segurança (confiança 3/10 — reclassificado como bug de correção) mas corrigido do mesmo jeito:** venda com pagamento dividido entre dois meios não-dinheiro (ex.: metade cartão, metade Pix) e devolução via `estorno_pagamento` mandava o valor total devolvido inteiro contra a *primeira* transação não-dinheiro encontrada, sem checar se aquela transação isolada cobria o valor — hoje inofensivo porque só existe o `MockPaymentProvider` (sempre aprova, sem gateway real conectado), mas seria recusado (ou pior, cobraria do lojista) contra um gateway de verdade. Corrigido: escolhe a transação de maior valor entre as não-dinheiro, e rejeita com erro claro se nem ela cobre o total, em vez de mandar pro provedor um valor que a transação nunca cobrou. Teste de regressão novo confirma a rejeição.
- Suíte completa (148 e2e) e build verdes com as duas correções aplicadas, antes do commit.

**Fase B do plano de fechamento de lacunas — recuperação de senha + bloqueio de conta (2026-08-19).** Segundo item do plano aprovado pelo usuário (ver Fase A/devolução acima). Nenhuma das duas existia: sem "esqueci minha senha", a única saída pra uma senha perdida era um dono resetar manualmente no banco; sem bloqueio de conta, o único freio contra tentativas de login era o rate-limit genérico de 5/min por IP (não protege contra tentativas distribuídas entre IPs).
- **Recuperação de senha copia o padrão já existente de convite de usuário** (`UsersService.inviteUser`/`acceptInvite`) quase literalmente: token opaco de 32 bytes (`randomBytes`), só o hash bcrypt persistido (`password_reset_tokens`, tabela nova, fora do RLS — mesmo grupo de `user_invites`/`refresh_tokens`, porque localizar o token acontece antes de existir contexto de tenant), TTL de 1h (bem mais curto que o convite, de 7 dias — é reset de conta já existente, não onboarding), uso único (`usedAt`), e o e-mail só é enviado dentro da mesma transação do insert do token (rollback se o envio falhar, nada de token "fantasma"). `AuthService.requestPasswordReset()` sempre responde sucesso, e-mail exista ou não — mesma disciplina anti-enumeração do `DUMMY_PASSWORD_HASH` do login (achado da revisão de 2026-08-18): o hash bcrypt do token roda mesmo sem usuário, igualando o custo de CPU; o tempo de envio real do e-mail (rede, Resend) é um resíduo aceito conscientemente, documentado no código — não dá pra fingir latência de um provedor de terceiro sem piorar a experiência de quem esqueceu a senha de verdade. Trocar a senha **revoga todos os refresh tokens do usuário** — sessões antigas (possivelmente comprometidas, é o cenário que motiva um reset) não sobrevivem à troca.
- **Bloqueio de conta**: `users` ganha `failed_login_attempts`/`locked_until`. Cinco tentativas erradas bloqueiam a conta por 15 minutos a partir da última tentativa (continuar tentando durante o bloqueio estende a janela, não é ignorado); login correto zera o contador. Complementa, não substitui, o rate-limit por IP existente — barra por **conta** mesmo se o atacante distribuir tentativas entre vários IPs.
- `EmailProvider` ganha `sendPasswordReset()` (mesmo padrão de `sendInvite`), implementado no adapter Resend e no mock. Endpoints públicos `POST /auth/forgot-password`/`reset-password`, ambos com o mesmo limite apertado do login (5/min). Frontend: `/esqueci-senha` e `/redefinir-senha`, mesmo layout de card único das páginas de auth existentes; link "Esqueci minha senha" adicionado à tela de login.
- 7 testes e2e (dois arquivos — `recuperacao-senha.e2e-spec.ts` e `bloqueio-conta.e2e-spec.ts`, separados de propósito: cada arquivo ganha sua própria instância da API e por consequência sua própria contagem de rate-limit em memória, e testar bloqueio de conta precisa de várias chamadas reais a `POST /auth/login` que não podem competir pelo mesmo orçamento de 5/min do teste de reset) cobrindo fluxo feliz (pede reset → troca senha → senha antiga para de funcionar → refresh token antigo revogado), token expirado, token reutilizado, e-mail inexistente (resposta idêntica), bloqueio na 5ª tentativa errada, zerar o contador em login bem-sucedido, e o teste de regressão do achado de segurança abaixo. Verificado também ao vivo: fluxo completo no navegador real (pedir reset, usar um token minerado direto contra o Postgres de dev já que o Resend real está configurado em `.env.local`, trocar a senha, confirmar senha antiga rejeitada e nova aceita), e o estado de link inválido em `/redefinir-senha` sem parâmetros.

**Revisão de segurança dedicada pós-recuperação-de-senha (2026-08-19)** — obrigatória por mexer em autenticação, rodada antes do commit. Metodologia de 2 etapas de novo (agente identifica → agentes independentes verificam cada achado sem confiar na descrição): 2 achados brutos, 1 sobreviveu ao filtro de confiança (≥8/10).
1. **Confirmado (confiança 9/10) — a mensagem de bloqueio de conta só aparecia quando a senha submetida estava CERTA, virando um oráculo de acerto de senha utilizável mesmo com a conta bloqueada.** O código checava `lockedUntil` só depois do branch `!passwordMatches` já ter decidido a resposta — ou seja, senha errada contra uma conta bloqueada sempre devolvia a mensagem genérica "E-mail ou senha inválidos", e só a senha CERTA chegava a "Conta temporariamente bloqueada...". Um atacante com uma credencial vazada conseguia confirmar que a senha estava certa bloqueando a conta de propósito (5 tentativas erradas) e mandando a senha candidata em seguida — sem nunca completar um login de verdade nem gerar nenhum evento de autenticação bem-sucedida pra alguém notar. O rate-limit de 5/min por IP do próprio login não bloqueia esse ataque de verdade: são só 6 requisições no total (5 pra bloquear + 1 pra testar), cabendo em duas janelas de 60s consecutivas com uma pequena espera no meio. Corrigido invertendo a ordem: o bloqueio é checado **antes** da senha decidir a resposta, com a mesma mensagem nos dois casos (`bcrypt.compare` continua rodando sempre, preservando a disciplina de tempo constante contra enumeração de e-mail que já existia). Teste de regressão novo prova que a mensagem é idêntica com senha certa ou errada enquanto a conta está bloqueada.
2. **Achado secundário, não confirmado (confiança 6/10 — abaixo do limiar de 8) — resíduo de canal-lateral de tempo em `POST /auth/forgot-password`.** Pra um e-mail cadastrado, a resposta espera o envio real pro Resend (rede, variável); pra um inexistente, responde quase na hora. Já era um resíduo **conscientemente documentado no próprio código** desde a implementação (não uma omissão), e a correção completa exigiria não esperar o envio do e-mail na resposta — o que abriria mão da garantia atual de "token nunca fica órfão se o envio falhar". Deixado como está por ora, com a ressalva já registrada no código de que é maior que o resíduo de bcrypt que motivou o `DUMMY_PASSWORD_HASH` original — candidato a revisitar se o produto algum dia justificar o trade-off.
- Suíte completa (155 e2e) e build verdes com a correção aplicada, antes do commit. Próxima revisão devida após 2-3 módulos ou a próxima mudança de dinheiro/auth (os próximos itens do mesmo plano — log de auditoria, exportação/anonimização LGPD — vão precisar da própria passada quando tocarem dado sensível/PII).

**Fase C do plano de fechamento de lacunas — log de auditoria (2026-08-19).** Terceiro item do plano (depois de devolução e recuperação de senha). Nenhuma ação sensível deixava rastro persistido — os únicos `Logger` do projeto eram efêmeros (console, nunca gravados em tabela), então uma investigação de incidente (quem trocou o papel de quem, quem concedeu qual exceção de permissão, quando uma assinatura foi cancelada) não tinha nenhum histórico pra consultar.
- **`audit_logs`** (tabela nova, com RLS — toda ação auditada é tenant-scoped): `tenantId`, `actorUserId` (nulo quando não há usuário autenticado por trás, ex. bloqueio de conta), `action` (string livre tipo `'user.role_updated'`), `targetType`/`targetId`, `metadata` (jsonb, só os campos relevantes de cada ação — nunca senha/token/corpo de requisição inteiro).
- **Chamadas explícitas nos pontos sensíveis já identificados, não um interceptor global automático** — mantém a lista do que é auditado intencional e evita logar por engano algo sensível que passe por um meio-termo genérico. Dois padrões, conforme o call site já tinha ou não uma transação própria: `AuditLogService.record()` (não-atômico, abre sua própria transação com contexto de tenant — usado em `UsersController.updateRole`, `PermissionOverridesController.create/remove`, `BillingController.subscribe/cancel`, todos controllers que nunca tinham transação nenhuma antes) e `recordTx()` (atômico, recebe a transação já aberta do call site — usado em `SaleReturnsService.create` e `AuthService.resetPassword`, comitando ou revertendo junto com a ação principal). `recordTx()` seta `app.tenant_id` de novo sempre, mesmo se o chamador já tiver feito isso — `audit_logs` tem `FORCE ROW LEVEL SECURITY`, e nem toda transação que precisa logar (ex. `resetPassword`, que mexe só em tabelas fora do RLS) já tem contexto de tenant setado.
- CASL: subject novo `'AuditLog'`, owner-only por design (não entra no `can('manage', [...])` do admin nem em `permissionSubjectSchema`) — ler o próprio log de auditoria não pode ser delegável, mesmo raciocínio de `'Tenant'`.
- Frontend: `/painel/auditoria`, tabela simples (data, ação traduzida, nome do autor resolvido contra `GET /users`, detalhes do metadata) — só visível pra owner, mesmo padrão de gate client-side de `/painel/assinatura`.
- 6 testes e2e cobrindo RBAC (só owner lê, admin/financeiro/operador de caixa rejeitados), evento não-atômico (troca de papel com ator/alvo/metadata corretos), evento atômico via `recordTx` (devolução de venda), evento de auto-serviço sem ator externo (reset de senha, ator é o próprio usuário), evento sem nenhum ator (bloqueio de conta), e isolamento entre tenants (RLS). Verificado também ao vivo: estado vazio ("Nenhuma ação registrada ainda"), e assinar um plano gerando e exibindo corretamente o evento `billing.subscribed` com autor e metadata `{"plan":"starter"}`.
- **Revisão de segurança dedicada (2026-08-19)**, rodada antes do commit — sem achados: confirmado que o subject `AuditLog` é genuinely owner-only (ausente do `admin` e de `permissionSubjectSchema`, a mesma classe de bug já corrigida duas vezes antes neste projeto para `Integration`/`UserAccess`), que `tenantId` em todo call site vem sempre do JWT verificado ou de uma leitura já escopada por tenant — nunca de input de cliente — então o `set_config` defensivo do `recordTx` não abre brecha de injeção de contexto entre tenants, e que nenhum `metadata` guarda segredo (senha, token, corpo de requisição inteiro).

**Fase D do plano de fechamento de lacunas — LGPD: exportação e anonimização de dados pessoais (2026-08-19).** Quarto e último item do plano. `docs/05-politica-de-privacidade-RASCUNHO.md` já prometia os direitos do art. 18 (acesso, portabilidade, eliminação) desde a Fase 0, mas nada disso existia em código. O PCAARB é **operador** dos dados dos clientes finais de uma loja — a ferramenta é self-service pro dono da loja (tenant), não um painel de superadmin.
- **Bug real encontrado e corrigido junto** (não só a feature nova): `CustomersService.remove()` fazia `DELETE` físico, que cascateava em `loyalty_ledger_entries` (FK `NOT NULL` com `onDelete: cascade`) — destruindo um ledger que o próprio schema documenta como imutável ("nunca UPDATE/DELETE de uma entrada já gravada"). A correção natural do direito de eliminação da LGPD (anonimizar em vez de apagar) resolve os dois problemas de uma vez: `remove()` agora checa se o cliente tem histórico (venda, ponto de fidelidade, lançamento financeiro) — sem histórico, apaga de verdade (nada a perder); com histórico, anonimiza (`name→'Cliente removido'`, `document/email/phone→null`, mesmo id) em vez de apagar, preservando a integridade de `sales`/`finance_entries` (histórico fiscal precisa sobreviver ~5 anos por lei) e do ledger de fidelidade.
- **`DataPrivacyService`/`DataPrivacyController`** (`data-privacy/customers/:id/export|anonymize`) somam a ferramenta explícita de atendimento a um pedido LGPD — não dependem do cliente ter ou não histórico, sempre anonimizam/exportam sob demanda. Export é um JSON (cliente + vendas com itens/pagamentos + ledger de fidelidade + lançamentos financeiros) baixado como arquivo, mesmo padrão `Content-Disposition` já usado pelos exports CSV de relatórios. CASL: subject novo `'DataPrivacy'`, owner-only (mesmo tratamento de `'AuditLog'` — ausente do `admin` e de `permissionSubjectSchema`).
- **Usuários (funcionários) ganham desativação** — não existia nenhuma forma de revogar acesso de um ex-funcionário além de trocar a senha manualmente. `users.active` (default true, mesmo padrão de `products.active`/`stores.active`) — nunca apagado de verdade, um usuário tem FK em vendas/estoque/caixa/auditoria por todo canto. `DELETE /users/:id` (mesmo subject `UserAccess` de `PATCH /:id/role`) desativa com as mesmas proteções de troca de papel: não pode desativar a própria conta, só um owner desativa outro owner, e nunca deixa o tenant sem nenhum owner ativo. Login bloqueado para conta inativa — mesma mensagem genérica de senha errada, nunca "conta desativada" (não é um oráculo novo: só dispara pra contas que existem, e a checagem roda depois do `bcrypt.compare` de tempo constante).
- Frontend: `/painel/cadastros` ganha "Exportar dados"/"Anonimizar" nas linhas de cliente (owner-only, client-side gate); `/painel/usuarios` ganha coluna "Status" e botão "Desativar" (oculto pra si mesmo).
- 6 testes e2e cobrindo cliente sem histórico apagado de verdade, cliente com histórico (venda + pontos) anonimizado sem cascatear no ledger, `anonymize` sob demanda owner-only, `export` owner-only com conteúdo correto, desativação bloqueando login e revogando sessão existente, e as proteções de auto-desativação/último-owner. Verificado também ao vivo: criar cliente, anonimizar (nome vira "Cliente removido", CPF/e-mail somem da tabela), e a tela de usuários mostrando a coluna Status corretamente.

**Revisão de segurança dedicada (2026-08-19)**, rodada antes do commit — 1 achado real confirmado, corrigido antes de commitar:
1. **Confirmado (confiança 9/10) — desativar um usuário não revogava a sessão já aberta dele, deixando acesso completo indefinidamente via `POST /auth/refresh`.** `UsersService.deactivate()` só marcava `active=false`; `AuthService.refresh()` nunca checava esse campo (só `login()` checava). Como cada chamada de refresh rotaciona pra um token novo de mais 7 dias, um ex-funcionário com o refresh token que já tinha no navegador (armazenado em `localStorage`, confirmado) mantinha acesso à API indefinidamente só continuando a chamar refresh — justamente o cenário que motiva a feature ("ex-funcionário desligado"). Corrigido revogando os refresh tokens do usuário na mesma transação que desativa (mesmo padrão já usado em `AuthService.resetPassword()` — o mecanismo já existia no projeto, só não tinha sido aplicado aqui), mais uma checagem defensiva de `active` no próprio `refresh()`. Teste de regressão novo prova que um refresh token emitido antes da desativação para de funcionar depois dela.
2. **Achado secundário, não confirmado (confiança 3/10 — corretamente filtrado como corrida teórica, não corrigido)**: o guard de "pelo menos um owner ativo" em `deactivate()` faz um SELECT de contagem seguido de um UPDATE, sem transação/lock — em teoria, dois owners desativando um ao outro exatamente ao mesmo tempo poderiam zerar os owners do tenant. Mesmo padrão já existe (e nunca foi corrigido) em `updateRole`, então não é uma lacuna nova desta fatia; exige dois donos já com privilégio máximo agindo um contra o outro, sem escalonamento de privilégio nenhum — fica anotado como possível melhoria de robustez futura, não uma correção deste commit.
- Suíte completa (167 e2e) e build verdes com a correção aplicada, antes do commit. Com isso, os quatro itens do plano de fechamento de lacunas (devolução/estorno, recuperação de senha/bloqueio de conta, log de auditoria, LGPD) estão implementados e testados.

**Auditoria de due diligence pós-plano + correção de bug real de receita (2026-08-19).** Com as quatro fases fechadas, em vez de partir direto pra mais um módulo, uma auditoria dedicada (agente de exploração, só leitura) verificou se os módulos novos de fato se integravam com o que já existia — não só se passavam nos próprios testes isolados. Achado real: **devolução parcial de venda não era refletida em nenhum relatório de receita.**
- `ReportsService.completedSalesInRange()` filtra `sales.status = 'completed'` e soma `sales.totalCents` direto. Devolução **total** funciona (a venda vira `status: 'canceled'` e some do filtro), mas devolução **parcial** mantém `status: 'completed'` por design (documentado desde a Fase A) — e nada descontava o valor já devolvido. Resultado: resumo de vendas, ranking de vendedor/loja/produto, curva ABC, relatório de comissão e a exportação CSV continuavam contando o valor **cheio** da venda depois de parte dele já ter voltado pro cliente — receita e comissão superestimadas, silenciosamente, pro resto da vida do relatório.
- Corrigido com dois helpers novos (`refundedCentsBySale`, no nível da venda; `returnedByLineItem`, no nível da linha, pra ranking de produto/reposição), somando `sale_returns.totalRefundedCents`/`sale_return_items.refundedCents` e descontando de toda soma de receita que passa por `completedSalesInRange` — a venda em si **não é mutada** (o registro original da transação continua íntegro, auditável), só a agregação do relatório desconta o que já foi devolvido. Efeito colateral correto e gratuito: `commissionReport` (que reusa a mesma agregação de `sellerRanking`) para de calcular comissão sobre receita já estornada, sem nenhuma mudança dedicada.
- A exportação CSV de vendas **não** mostra um "Total" já líquido — mantém o valor original da transação (rastro auditável pro contador) e ganha uma coluna nova, "Valor devolvido", separada, pra quem usa a planilha decidir como netar.
- Auditoria também confirmou (sem achado): vendas importadas via adapter de marketplace não têm `sales.id` próprio (só gravam em `marketplace_orders`), então estruturalmente não entram no fluxo de devolução — gap de feature conhecido, não bug; `sale_returns`/`sale_return_items` não têm `storeId` denormalizado, mas nada no projeto usa loja como fronteira de RBAC (é só dimensão de relatório), então não é uma inconsistência nova; pipeline de CI (`.github/workflows/ci.yml`) continua com trigger/env vars corretos.
- Teste de regressão novo em `reports.e2e-spec.ts` cobrindo o cenário exato (venda de 3 unidades, devolução parcial de 1, conferindo resumo/ranking de vendedor/ranking de loja/comissão/CSV todos líquidos, e a venda continuando `completed`). Suíte completa (168 e2e) e build verdes. Verificado também ao vivo: venda de R$30 (3×R$10), devolução parcial de R$10, e a tela de Relatórios caindo de R$30 para R$20 de faturamento em tempo real — mesmo valor no resumo, ranking de vendedor, ranking de loja e curva ABC; CSV exportado com `Total=30.00;Valor devolvido=10.00` na mesma linha.

## Como rodar localmente

```bash
pnpm install
docker compose up -d          # sobe Postgres e Redis
cp apps/api/.env.example apps/api/.env.local        # ajuste os segredos JWT
cp apps/web/.env.example apps/web/.env.local
pnpm db:migrate                # aplica as migrations do Drizzle
pnpm dev                       # API em :3001, Web em :3000
```

> **Porta ocupada?** O `docker-compose.yml` publica Postgres em `5433` e Redis em `6380` (em vez das portas padrão `5432`/`6379`) porque é comum já haver outro Postgres/Redis rodando na máquina (nativo, outra distro WSL etc.), o que causa falha de autenticação silenciosa por conectar no serviço errado. Se sua máquina não tem esse conflito, pode usar as portas padrão à vontade — só ajuste `DATABASE_URL` e o compose.

> **Duas URLs de banco?** `DATABASE_URL` (dono das tabelas) é usada só por `pnpm db:migrate`/`db:generate`. `APP_DATABASE_URL` é a conexão de runtime da API, numa role restrita (`pcaarb_app`, sem `SUPERUSER`/`BYPASSRLS`) criada pela migration `0011_app_role_least_privilege`. Rode `pnpm db:migrate` antes de subir a API — sem essa migration a role não existe e a API não sobe.
