# PCAARB

SaaS de gestão empresarial com PDV (frente de caixa), inspirado na TOTVS — modular, multi-tenant, começando enxuto e evoluindo para um ERP completo.

## Status atual

**Fase 0 (fundação) concluída.** Monorepo, auth multi-tenant (registro/login/refresh com trial), RBAC via CASL, RLS no Postgres, CI — tudo validado contra banco real.

**Fase 1 (MVP comercial) concluída** — Cadastros, PDV, Estoque básico, Financeiro básico, fiscal e pagamento integrado (sandbox), job de trial e gestão de usuários:

- **Cadastros:** categorias, produtos, clientes e fornecedores — CRUD completo, multi-tenant de verdade via RLS, RBAC via CASL (`operador_caixa` só lê; `admin`/`owner` gerenciam; `financeiro` só lê). Preço sempre em centavos (inteiro), nunca float. Produto não tem exclusão definitiva — só `active: false` — porque venda referencia produto e apagar quebraria histórico.
- **PDV:** abertura/fechamento de caixa, sangria/suprimento, venda de balcão com múltiplos itens e pagamento dividido entre formas (dinheiro/cartão/Pix). Venda exige caixa aberto do próprio operador; total da venda precisa bater exatamente com a soma dos pagamentos informados; item de venda guarda snapshot do nome/preço do produto (preço pode mudar depois, histórico não). Quantidade é sempre inteira — venda fracionada/por peso fica para quando o público-alvo (mercearia, loja, pet shop, farmácia, conveniência) exigir.
- **Estoque básico:** entrada, saída e ajuste de saldo por produto, com ledger auditável (`stock_movements`) e saldo denormalizado no próprio produto. Venda no PDV desconta o estoque automaticamente dentro da mesma transação (ou os dois acontecem, ou nenhum) e bloqueia a venda se não houver saldo suficiente. Produtos podem opcionalmente sair do controle de estoque (`trackStock: false`) para itens sob encomenda ou serviços. Movimentação manual é restrita a `admin`/`owner` (`financeiro` só lê; `operador_caixa` não movimenta diretamente, só via venda).
- **Financeiro básico:** contas a pagar e a receber (`finance_entries`) com vencimento, status (pendente/paga/cancelada) e vínculo opcional a cliente ou fornecedor. Pagamento é sempre integral — sem pagamento parcial na Fase 1. Resumo de fluxo de caixa (`GET /finance-entries/summary`) soma pendente, vencido e realizado (pago) por tipo. Gestão é exclusiva de `admin`/`owner`/`financeiro`; `operador_caixa` não acessa. Contas ainda não se conectam a vendas a prazo — é um ledger manual independente do PDV por enquanto.
- **Fiscal e pagamento integrado (sandbox):** seguindo a recomendação do [docs/03](docs/03-build-vs-buy-pagamentos-fiscal.md), o resto do sistema fala com interfaces internas (`PaymentProvider`, `FiscalProvider`), não com o gateway/fiscal diretamente — trocar de fornecedor é escrever um adapter novo. Hoje ambas usam um adapter mock (nenhuma conta/credencial de parceiro existe ainda): pagamento em cartão/Pix é "cobrado" e recebe um `providerTransactionId`; toda venda emite automaticamente uma NFC-e simulada (`fiscal_documents`, chave de 44 dígitos) sem travar a venda se o "provedor" falhar (contingência) — nesse caso fica com status `rejected` e pode ser reemitida via `POST /sales/:id/fiscal-document/retry` (só `admin`/`owner`). Pagamento recusado pelo gateway cancela a venda inteira (mesma transação do estoque/itens). Ir para produção real exige só trocar o adapter por Pagar.me/Mercado Pago e Focus NFe/PlugNotas/eNotas, quando houver conta e credenciais.
- **Job de expiração de trial:** roda de hora em hora (`@nestjs/schedule`) e sincroniza `tenants.status` para `blocked` quando o trial vence. O bloqueio de acesso em si já era em tempo real (`TenantStatusGuard` compara `trialEndsAt` a cada request) — o job só mantém o status persistido fiel à realidade.
- **Gestão de usuários:** convite por e-mail (Resend) com token de uso único (hash bcrypt, expira em 7 dias, `/painel/usuarios`), aceite com login automático (`/aceitar-convite`), promoção/rebaixamento de papel com a regra de sempre existir ao menos um `owner` por tenant. Só `admin`/`owner` gerenciam usuários; só um `owner` pode convidar/promover outro `owner`. Segue o mesmo padrão de adapter interno (`EmailProvider`) do pagamento/fiscal — trocar de provedor de e-mail é só a classe.
- Frontend: `/painel/produtos` (cadastro + saldo de estoque + movimentação), `/painel/pdv` (abrir caixa, montar carrinho, pagamento dividido, sangria/suprimento, fechar caixa, confirmação de NFC-e sandbox), `/painel/financeiro` (contas a pagar/receber + resumo de fluxo de caixa) e `/painel/usuarios` (convidar, listar, promover/rebaixar)
- 49 testes e2e contra Postgres real cobrindo CRUD, isolamento entre tenants (RLS — inclusive um teste que verifica o privilégio da própria role de banco, não só o filtro da aplicação), RBAC, regras de negócio do PDV, desconto atômico de estoque, ciclo de vida financeiro, emissão fiscal (contingência/reemissão), recusa de pagamento pelo gateway, expiração de trial, convite/gestão de usuários (incluindo atomicidade quando o envio de e-mail falha) e logout/revogação de refresh token

Com isso os seis itens de Fase 1 do roadmap estão implementados, as duas pendências que ficavam para depois (trial automático, gestão de usuários) foram fechadas, e uma falha crítica de isolamento entre tenants foi encontrada e corrigida (a role de banco usada em runtime era superuser e ignorava RLS por completo — ver migration `0011_app_role_least_privilege`). O que falta para produção real de fiscal/pagamento é uma decisão de negócio (qual parceiro, criar a conta) — não código; ver [docs/03](docs/03-build-vs-buy-pagamentos-fiscal.md).

**Hardening de segurança pós-revisão:** o código foi auditado (revisão automatizada + IA externa) antes de ir para o GitHub público. Achados reais corrigidos: `updateRole` tinha dois bypasses de autorização (admin rebaixando owner; usuário rebaixado se auto-promovendo com o access token antigo antes de expirar); o e-mail de convite interpolava nome do convidante/empresa sem escape de HTML (injeção de link de phishing num e-mail assinado); não havia como revogar um refresh token (só rotação no uso — `POST /auth/logout` agora existe e é chamado pelo botão "Sair"); faltavam headers de segurança (`helmet`); `register`/`invite`/`accept-invite` só tinham o rate-limit genérico da API (100/min), agora têm limite próprio; `CORS_ORIGIN` não era validado como URL. Itens reais mas adiados por serem features maiores, não fixes pontuais: reset de senha, 2FA, bloqueio de conta após tentativas falhas, log de auditoria de ações privilegiadas — ver issues/roadmap.

**Fase 2 (consolidação) — em andamento.** Primeiro módulo: **Compras**.

- **Compras:** pedido de compra a fornecedor (`purchase_orders`/`purchase_order_items`, snapshot de nome/custo do produto no momento do pedido, mesmo padrão de `sale_items`) com três estados — `draft` (rascunho, editável só por recriação), `received` (recebido) e `canceled` (só a partir de rascunho). Sem estado "enviado ao fornecedor": não existe integração real de notificação ainda, um status sem comportamento por trás seria estado morto (mesmo raciocínio do sandbox fiscal/pagamento). Receber um pedido é atômico com o Estoque: gera entrada (`stock_movements`, reaproveitando `StockService.applyMovement`) para cada item com `trackStock` ativo, e atualiza `products.costPriceCents` com o último custo de compra. Cancelamento só é permitido em rascunho (recebido não se desfaz sozinho — evita ter que reverter estoque). RBAC via CASL: `admin`/`owner` gerenciam, `financeiro` só lê (cuida de custo), `operador_caixa` sem acesso. Frontend em `/painel/compras`. Deliberadamente desacoplado do Financeiro por ora — receber um pedido não gera conta a pagar automaticamente (o usuário lança manualmente se quiser); acoplar os dois é decisão para quando "Financeiro avançado" (outro item da Fase 2) entrar.
- 6 testes e2e novos cobrindo o fluxo completo (criar → receber → estoque/custo atualizados), transições de estado inválidas, isolamento entre tenants e RBAC.
- 5 testes e2e novos para Relatórios cobrindo agregação correta (resumo/ranking/curva ABC), período vazio, validação de formato de data, isolamento entre tenants e RBAC.
- 6 testes e2e novos para Inventário cobrindo o fluxo completo (abrir → contar → finalizar → estoque ajustado), reconciliação contra saldo concorrente (movimentação durante a contagem), filtro de produto ativo/`trackStock`, transições de estado inválidas, isolamento entre tenants e RBAC.
- 5 testes e2e novos para Centro de custo/DRE cobrindo vínculo com conta financeira e agregação correta no DRE, centro de custo inexistente, desativação sem quebrar histórico, isolamento entre tenants e RBAC.
- **Cadastros (Clientes/Fornecedores):** o CRUD de `customers`/`suppliers` já existia por completo desde a Fase 1, mas sem nenhuma tela — cliente só entrava via API direta, o que ficou evidente ao testar o módulo de Compras (não dava pra escolher fornecedor sem ter cadastrado um antes). `/painel/cadastros` fecha essa lacuna com abas Clientes/Fornecedores (criar + listar + excluir), reaproveitando o mesmo padrão visual das outras páginas.
- **Relatórios/BI básico:** primeiro corte de BI usando dados que o PDV já gera (`sales`/`sale_items`), sem nenhuma infra nova — `GET /reports/vendas-resumo|produtos-ranking|curva-abc|vendedores-ranking`, todos aceitando `?from=&to=` (padrão: últimos 30 dias) e considerando só vendas com status `completed`. Curva ABC usa o corte clássico por receita acumulada (A até 80%, B até 95%, C o resto). RBAC via CASL (`Report`): `admin`/`owner`/`financeiro` leem, `operador_caixa` não acessa — mesma lógica de sensibilidade de dado financeiro do `FinanceEntry`. Frontend em `/painel/relatorios` com filtro de período, cards de resumo, ranking de vendedores e a curva ABC com badge de classe por produto.
- **Estoque avançado (inventário):** do escopo original de "Estoque avançado" do roadmap, só a parte que faz sentido pra uma loja única — contagem física de estoque (`stock_counts`/`stock_count_items`). "Múltiplos depósitos" e "transferência entre lojas" pressupõem multi-loja, que é item de Fase 3 (Expansão); implementar isso agora seria estado morto, mesmo raciocínio já aplicado ao "enviado" do Compras. Fluxo: abrir uma contagem tira uma foto de todos os produtos ativos com `trackStock`, o operador vai preenchendo a quantidade contada por item, e ao finalizar o sistema gera um ajuste (`StockService.applyMovement`, tipo `ajuste`) para cada item contado — recalculado contra o saldo **atual** do produto no momento da finalização (não o saldo congelado na abertura), pra não apagar uma venda ou recebimento de compra que aconteça no meio da contagem. Itens não contados ficam como estão, sem forçar contagem completa de tudo de uma vez. RBAC igual ao de `StockMovement`: `admin`/`owner` abrem/finalizam/cancelam, `financeiro` só lê, `operador_caixa` sem acesso. Frontend em `/painel/contagens`.
- **Financeiro avançado — centro de custo e DRE simplificado:** `cost_centers` é um cadastro simples (nome + ativo, sem exclusão definitiva) que `finance_entries` referencia opcionalmente. DRE simplificado (`GET /reports/dre`, mesmo módulo de Relatórios) soma receitas e despesas **já pagas** no período — regime de caixa, não de competência, porque não existe conciliação bancária real ainda; é mais honesto mostrar só o que efetivamente aconteceu do que fingir uma competência que o sistema não rastreia direito. Quebra o resultado por centro de custo, com um bucket "Sem centro de custo" pra contas sem classificação. RBAC: `admin`/`owner`/`financeiro` gerenciam centro de custo (mesmo grupo que já gerencia `FinanceEntry`), `operador_caixa` sem acesso. **Conciliação bancária ficou de fora deste corte** — importar/casar extrato OFX é alto esforço e incerteza sem uma conta bancária real conectada (mesmo raciocínio de adiar parceiro de pagamento/fiscal reais); revisitar quando houver essa integração.

## Como rodar localmente

```bash
pnpm install
docker compose up -d          # sobe Postgres e Redis
cp apps/api/.env.example apps/api/.env.local        # ajuste os segredos JWT
cp apps/web/.env.example apps/web/.env.local
pnpm db:migrate                # aplica as migrations do Drizzle
pnpm dev                       # API em :3001, Web em :3000
```

> **Porta ocupada?** O `docker-compose.yml` publica Postgres em `5433` e Redis em `6380` (em vez das portas padrão `5432`/`6379`) porque é comum já haver outro Postgres/Redis rodando na máquina (nativo, outra distro WSL etc.), o que causa falha de autenticação silenciosa por conectar no serviço errado. Se sua máquina não tem esse conflito, pode usar as portas padrão à vontade — só ajuste `DATABASE_URL` e o compose.

> **Duas URLs de banco?** `DATABASE_URL` (dono das tabelas) é usada só por `pnpm db:migrate`/`db:generate`. `APP_DATABASE_URL` é a conexão de runtime da API, numa role restrita (`pcaarb_app`, sem `SUPERUSER`/`BYPASSRLS`) criada pela migration `0011_app_role_least_privilege`. Rode `pnpm db:migrate` antes de subir a API — sem essa migration a role não existe e a API não sobe.
