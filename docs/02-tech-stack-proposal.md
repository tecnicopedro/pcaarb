# PCAARB — Technology Stack Proposal

*English version of [the original Portuguese proposal](02-stack-tecnologico.md).*

> **This document exists for confirmation before coding started.** Where more than one reasonable option existed, the alternative considered and why it wasn't chosen is listed — so a specific point could be disagreed with without rejecting the whole package.

> **Note (2026-08-18):** this is the original proposal document, written before Phase 0 — kept as a record of the reasoning behind the choices, not as current status. For what was actually implemented, [README.md](../README.md) (or [README.pt-BR.md](../README.pt-BR.md) for the full log) is the source of truth, updated with every module shipped. A few points below diverged from the proposal during real implementation, because the need that justified them never materialized at this scale — none of them block anything today, but worth knowing before assuming they're in place:
> - **BullMQ + Redis (section 3):** not used. Fiscal issuance, payment, and invite email all run synchronously within the request itself (with contingency/manual retry where it makes sense, not a queue) — sufficient at the current volume; revisit if any of these steps gets slow enough to justify a queue's operational complexity.
> - **Playwright as a committed automated E2E suite (section 7):** doesn't exist as a committed suite. The real automated tests are Vitest + Supertest against the real API (`apps/api/test/`, running in CI). Playwright is used during development sessions for live manual frontend verification, not as tests that run unattended.
> - **2FA (section 6) and an audit log for privileged actions (section 11):** deliberately deferred, not forgotten — see the security-hardening sections of the README for the full list of consciously deferred items (the audit log has since shipped — see the README's status log).
> - **Observability — Sentry/OpenTelemetry/Better Stack (section 10):** not yet instrumented.
> - **Dependabot/Snyk (section 11):** Dependabot is configured (`.github/dependabot.yml`, npm + GitHub Actions); Snyk is not.
> - **CI/CD (section 8):** lint/typecheck/test/e2e/build now genuinely run on every push/PR (`.github/workflows/ci.yml`) — but automatic deployment to staging/production doesn't exist: no production environment has been provisioned yet.

## 1. Requirements that guided the choice

The stack needed to account for: version control, security, validation, testing, performance, quality, and front↔back communication flexibility. On top of that, a real project constraint: **low initial budget, without giving up quality** — i.e., prioritize tools with a free tier/low cost at small scale that won't require a rewrite once scale grows.

## 2. Architecture overview

- **Monorepo** (pnpm workspaces + Turborepo): backend, frontend, and shared packages (types, validation) in the same repository. Avoids duplicating API contracts and lets one PR change back and front together with end-to-end type safety.
- **Modular monolith** to start: a single backend service organized into domain modules (Sales, Inventory, Finance, Fiscal...) with clear internal boundaries. We won't move to microservices early — that would add operational complexity that doesn't pay off at the project's current size. Internal modularity makes it possible to extract a module into its own service later, if any module needs to scale independently (e.g., asynchronous fiscal issuance).
- **Multi-tenant:** shared database, shared schema, isolation via `tenant_id` + PostgreSQL Row-Level Security. Cheaper than schema-per-tenant and sufficient for the volume expected over the next 1–2 years; can evolve to schema-per-tenant for specific large customers later, without rewriting the application.

## 3. Backend

| Layer | Choice | Why |
|---|---|---|
| Language | TypeScript | Same data types from front to back; reduces API contract bugs |
| Framework | **NestJS** | Native modular structure (matches the domain architecture above), DI, guards ready for RBAC/multi-tenant, auto-generates OpenAPI, testable by default |
| ORM / data access | **Drizzle ORM** + PostgreSQL | Thin, SQL-like layer, better performance and predictability than "magic" ORMs on complex queries (reports, finance) — important since "performance" was an explicit requirement |
| Validation | **Zod** | The same validation schema is reused on the front (forms) and the back (DTOs) — eliminates duplication and avoids "the back validates one thing, the front another" |
| Async queue/jobs | **BullMQ + Redis** | Fiscal issuance, emails, heavy reports run in the background without blocking a sale at the POS |
| Public API | REST + OpenAPI (Swagger) | Universal standard, essential for Phase 4 (public/partner API); OpenAPI auto-generated by NestJS |

**Alternative considered — Prisma ORM:** better initial DX (less code), but historically slower on complex queries and with less fine-grained control over generated SQL — works against the performance requirement, especially for financial reports. Kept as a plan B if the team finds Drizzle too verbose in practice.

**Alternative considered — GraphQL/tRPC instead of REST:** tRPC would be faster to develop between TypeScript front and back, but locks communication to TypeScript clients — would make Phase 4's public API unworkable without a second layer later. REST with OpenAPI is ready for external consumption from the start.

## 4. Frontend (admin panel and back office)

| Layer | Choice | Why |
|---|---|---|
| Framework | **Next.js (App Router) + TypeScript** | Server components reduce JS shipped to the browser (performance), good SEO if we ever have public pages (e.g., a storefront page) |
| UI | **Tailwind CSS + shadcn/ui** | Accessible, consistent components, no license lock-in, allows building a distinct visual identity on top without reinventing every component from scratch |
| Server data/state | **TanStack Query** | Cache, revalidation, and standardized loading/error states across screens |
| Form validation | **Zod + React Hook Form** | The same Zod schema from the backend, reused |

## 5. POS (point-of-sale terminal)

The POS has a requirement the admin panel doesn't: **it needs to keep selling with unstable internet.**

- **Phase 1 (MVP):** a PWA (Progressive Web App) built on the same Next.js base, with a service worker caching essential data (products, prices) and a local sale queue to sync once the connection returns. Fast to ship, runs on any computer/tablet with nothing to install.
- **Phase 3 (serious offline-first):** evaluate migrating the POS client to **Tauri** (a lightweight desktop app, Rust + webview based, much lighter than Electron) with a local database (SQLite) and bidirectional sync — the level of robustness a physical store's operation genuinely needs when the internet drops mid-shift.

## 6. Authentication and authorization

- **Short-lived JWT + refresh token**, issued by the NestJS backend itself (Passport.js underneath).
- **RBAC with CASL** for granular permissions per module/action (e.g., a cashier doesn't see the finance module).
- **Multi-tenant isolation enforced at two levels:** an application guard (every request carries a resolved tenant) + PostgreSQL Row-Level Security (defense in depth — even an application bug can't leak data across tenants).
- **Optional 2FA** from Phase 0 for administrative accounts (given the fraud risk in financial/POS systems).

**Alternative considered — Keycloak or Clerk/WorkOS (auth-as-a-service):** provide ready-made enterprise SSO, but per-active-user cost penalizes exactly the "many store owners paying little each" scenario. Kept as an option for enterprise SSO in Phase 4, not as the system's foundation.

## 7. Testing

| Type | Tool | Covers |
|---|---|---|
| Unit | Vitest | Isolated business rules (tax calculation, sale totals, etc.) |
| Integration | Vitest + Supertest | API endpoints against a real test database (not mocked) |
| E2E | Playwright | Critical flows: open register → sell → close register; NFC-e issuance; reconciliation |
| Contract | Shared Zod schemas | Guarantees front and back never drift from the API contract |

Finance and fiscal modules carry a higher mandatory test-coverage bar than the rest — that's where a bug costs the customer real money.

## 8. CI/CD and environments

- **GitHub Actions:** lint, tests, build, and type-checking on every PR; automatic deploy on merge to `main` (staging) and by tag to production.
- **Docker** to package the backend identically across all environments.
- Three environments: `dev` (local), `staging`, `production`.

## 9. Infrastructure and hosting

**Initial phase (low cost, no dedicated infra team):**
- **Railway** or **Fly.io** to host the backend + a managed Postgres database — simple deploys, predictable low cost at small scale, no Kubernetes/Terraform knowledge required.
- Frontend on **Vercel** (native Next.js integration, generous free tier).

**Growth phase (once volume justifies it):**
- Migration to **AWS or GCP** with Terraform (infrastructure as code), once managed-service cost exceeds the cost of running the infrastructure ourselves — typically only pays off past tens of thousands of reais/month in hosting, so it's not a priority now.

## 10. Observability

- **Sentry** (free tier) for production errors, front and back.
- **OpenTelemetry** instrumenting the backend from the start (even without an expensive destination early on) — avoids having to re-instrument later.
- **Better Stack or Axiom** (free tier) for centralized logs once local logging is outgrown.

## 11. Security

- OWASP ASVS checklist at a level appropriate for a financial application (not optional given the system handles the store owner's money).
- Rate limiting and brute-force protection on login (`@nestjs/throttler`).
- Secrets out of the code (environment variables + Doppler or an equivalent free tool early on).
- Dependabot/Snyk (free tier) for vulnerable-dependency scanning.
- Audit log for every financial/fiscal action (who did what, when) — a trust requirement for a POS system, and likely a legal requirement depending on the module.
- **LGPD** (Brazil's GDPR-equivalent) compliance designed into customer/CRM data from the start (Phase 3), not retrofitted.

## 12. Summary — what needed confirmation

1. Monorepo + modular monolith (not microservices) to start — ✅ recommended
2. NestJS + TypeScript on the backend — ✅ recommended
3. Drizzle ORM (instead of Prisma) — the point most open to disagreement if more DX and less manual SQL is preferred
4. Next.js + Tailwind + shadcn/ui on the front — ✅ recommended
5. PWA for the POS in Phase 1, Tauri only in Phase 3 — ✅ recommended (avoids early over-engineering)
6. In-house auth (JWT+RBAC) instead of Keycloak/Clerk — ✅ recommended for cost reasons
7. Railway/Fly.io + Vercel at first, migration to AWS/GCP only once cost justifies it — ✅ recommended
